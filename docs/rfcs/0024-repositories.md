# RFC: Repositories — packaging canonical game systems and world content for reuse across tenants

Status: proposed

## Context

[docs/domain/repositories.md](../domain/repositories.md) describes what a repository *is*, in plain language: a reusable setting — a published game system, a homebrew world, or an entire multiverse — that a game can draw on, read live, or copy and diverge from. Nothing has ever designed how. [RFC 0001](0001-core-domain-data-model.md)'s own open question #2 named the core problem directly: prototypes sourced from a shared repository "need to be usable by many tenants without actually living inside any one of them — a plain `entity.tenant_id` can't represent that," and left the likely shape ("repository content lives in its own, separately-authored tables outside the tenant-scoped graph entirely") as a guess, not a design. Open question #3 (multi-game-system stats) separately guessed that the fix might not need a new scoping column at all, and could instead reuse prototype inheritance — a system-agnostic "Sword" with "Sword (D&D 5e)"/"Sword (Blades in the Dark)" variants inheriting from it. [RFC 0018](0018-entity-template.md) (entity_template, proposed, not yet built) independently deferred "cross-tenant, reusable game-system templates" as the same still-open question, and named a not-yet-existing "repository author" role, expected to "eventually own template (and computed-stat) authoring, with a tenant admin subscribing to (copying from) a repository rather than authoring from scratch."

A concrete request sharpened this from an abstract gap into a real proposal: repositories should be able to package **game systems** (mechanical definitions — stat groups, entity ancestries, information types — that a tenant subscribes to and gets copied into its own tenant-specific, editable data), **game content** (a setting's own pre-populated pseudo-entities — NPCs, locations, items), and **bridge repositories** that connect the two by providing a setting's entities with a specific system's stats (`dnd_faerun`, `pathfinder_faerun`, and `shadowdark_faerun` all bridging the same Faerûn content into three different rule systems). This RFC resolves RFC 0001's open question #2 concretely, confirms and operationalizes its guess at question #3, and names — without solving — the way this makes RFC 0001's still-open question #4 (campaign-relevance of world content, "facts") newly urgent.

This design was produced through a structured, adversarial debate among five independently-researched perspectives (a technical/platform view; a tenant owner/admin view; a GM view; a player view; an author/worldbuilder view) run across three full rounds. One participant (the worldbuilder perspective) initially argued for a materially different shape — repository content as its own first-class thing, never tenant data at all — and, under cross-examination, reversed that position after stress-testing their own alternative as rigorously as they'd stress-tested the consensus and finding it held up worse. The reversal, and the concrete engineering answers that produced it, are folded into the Decision below rather than narrated separately.

## Decision

### 1. A repository is a tenant — specifically, one nobody plays a live game in

`tenant` gains a `kind` column: enum `play` (default) | `repository`. A `kind = repository` tenant never has `Campaign` or `Player` rows — gated at the application layer for this slice (a CHECK/trigger can follow once the shape is proven in practice). This was the most contested single decision in the whole design, and is worth stating plainly why it won over keeping repository content in its own tables outside the tenant graph entirely:

- **Reuse is real, not aspirational.** `entity` and its whole component/extension family — concrete kinds, prototype inheritance (cycle-prevented), stat values, containment, information/payloads; the complete list is in §4 — plus every view built over them (`v_effective_stat`, ADR 0037/0039), work unmodified. A parallel, non-tenant-scoped schema would need every one of these — the cycle-prevention trigger, the recursive stat resolution, the class-table-inheritance payload shape — taught to also traverse a second graph, forever, for every future feature that touches entities.
- **The alternative's own strongest form was tried and found worse.** A single `entity` table with a `repository_id` column as an alternative to `tenant_id` (one shared graph, not a parallel schema) was proposed and stress-tested directly. It fails on a different, more dangerous axis than the one it was meant to avoid: every existing query, view, and RLS policy that currently treats `tenant_id` as *the* scoping column would need to learn a second, mutually-exclusive case — most consequentially `v_effective_stat`'s own recursive prototype resolution, the most complex and performance-sensitive query in the domain model. A missed branch there is a silent, unenumerable failure (an inherited stat quietly resolves wrong) rather than a loud, obvious one (a repository shows up somewhere in an admin screen it shouldn't). The tenant-flavored approach is additive purely at the **policy** layer — invisible to every query and view that already exists — rather than at the **schema** layer, visible to all of them.

### 2. Authorship is Membership on the repository-tenant, for now — explicitly not the final answer

Whoever holds `Membership(role=OWNER)` on a `kind=repository` tenant can edit its content. This is RFC 0018's still-unbuilt "repository author" role, and it costs nothing new to stand up: invitations, notifications, and the tenant admin surfaces already work. It is **not** claimed to be free, and it is **not** the final design — see [Not in Scope](#not-in-scope).

**Hard invariant, enforced at the data layer, not just by convention**: `tenant.kind` is immutable after creation (or settable only while the tenant holds zero content — the exact mechanism is an implementation choice, not a design one). This is required specifically so an existing, populated play-tenant can never be "promoted" into a repository after the fact — publishing always means creating a fresh, distinct tenant. Without this, someone could route around every other guardrail in this document by simply relabeling a live tenant. This is what makes the concrete case that motivated re-opening this question — a solo worldbuilder who also runs unrelated solo campaigns needing to share exactly one setting with co-authors, without exposing those unrelated campaigns — actually hold: the shared setting lives in its own, purpose-created repository-tenant from the start; nobody is ever a member of the worldbuilder's personal tenant, and tenant-to-tenant RLS isolation between the two is exactly as strong as between any two unrelated tenants today, because nothing about this design weakens it.

### 3. `repository_subscription` — the only new access-control table

`repository_subscription(repository_tenant_id, subscriber_tenant_id, mode: live | frozen, created_at, created_by)`. A DB-enforced trigger CHECK requires `repository_tenant_id` to reference a `tenant.kind = 'repository'` row. This is the single mechanism that makes the RLS extension below safe by construction rather than by discipline: the exception is **structurally incapable** of granting one ordinary tenant read access into another ordinary tenant, independent of whether every future line of application code gets it right.

### 4. A second, narrow, read-only RLS policy on every table repository content can populate — not six, a complete family

An earlier draft of this section named six tables by picking one representative per concern and missed this codebase's own class-table-inheritance pattern, where a "concept" is usually two or more tables — a definition/base table plus its value, acquisition, or concrete-extension siblings. Naming `stat_group`/`stat_definition` (what a stat *is*) but not `entity_stat` (what value an entity actually *has* for it) would have meant a bridge repository's whole reason for existing — attaching concrete stat values to a setting's entities — couldn't be read across the subscription boundary at all. The complete, correct set:

- `entity` itself.
- Its concrete-kind extensions: `item`, `item_instance`, `being`, `character` — and any future concrete kind added the same way.
- The component tables that attach data to an entity by `entity_id`: `entity_prototype`, `entity_stat_group`, `entity_stat`, `containment`, `information`.
- The concrete extensions of those components: `payload`'s four kinds (`payload_description`, `payload_number`, `payload_picture`, `payload_document`).

Each gains a second, additive, `FOR SELECT`-only permissive policy alongside its existing `tenant_id = your own` policy, of the same shape:

```sql
CREATE POLICY repository_read ON entity FOR SELECT
  USING (tenant_id IN (
    SELECT repository_tenant_id FROM repository_subscription
    WHERE subscriber_tenant_id = current_setting('app.tenant_id')::uuid
  ));
```

**Deliberately excluded, and why**: `knowledge`/`group_member` — repository content has no real characters or players to be a knower, so per §10 there is nothing for these tables to hold. `ownership` — repository content has no player-controlled characters to own anything; an NPC "holding" an item within a repository is `containment`, not `ownership`. Anything campaign/membership/notification-shaped (`campaign`, `player`, `membership`, `character_player`, `campaign_gm`, `notification`, `audit_log`, ...) — a repository-tenant never holds rows in any of these by construction (§1).

**This is a consequence of a rule, not a fixed list to remember.** Any table that is `entity` itself, a class-table-inheritance extension of it, a component attached to an entity by `entity_id`, or a class-table-inheritance extension of one of those components, needs this same second policy. A future concrete entity kind or payload kind that skips it reopens exactly the gap this correction just closed — the same discipline [RFC 0001](0001-core-domain-data-model.md) already asks for with its "every concrete type gets a view, kept in sync, or the core's flexibility becomes a readability tax" rule, one layer further down.

Postgres ORs multiple permissive policies together automatically. The base policy's own `WITH CHECK` is untouched on every one of these tables — writes can never target a subscribed-to repository, even under a buggy `USING` clause, because the write path never changes at all. Two further requirements, named as **required scope for this RFC's implementation, not optional hardening**:

- The exception policy is `FOR SELECT` only, never `FOR ALL`. Its worst-case failure mode is leaking already-published read access, never a write.
- This codebase already has a standing, per-table convention of directly testing RLS isolation (`test_entity.py`, `test_entity_prototype.py`, `test_containment.py`, `test_information.py`, `test_knowledge.py` all assert tenant-isolation behavior against `current_setting('app.tenant_id')` today). Extend it with two new assertions per affected table: *no subscription row exists → zero cross-tenant visibility*, and *a subscription row exists → SELECT-only visibility, writes still rejected*. A future refactor that breaks isolation breaks this suite mechanically, every time — this is what "safe by construction" means in a codebase with real CI gates, as distinct from a policy whose safety depends on being carefully re-read during every future change nearby.

Whether this two-policy shape is a smaller, safer version of a "cross-tenant read" than a live gameplay-resolution read across tenants would be — rather than the same risk in a thinner disguise — was challenged directly during this design's review and is worth answering plainly, since it is the same underlying primitive the earlier "cross-tenant repositories" question deliberately fenced off pending its own RFC: **yes, it is the same primitive**, and this is that RFC. What makes it a different proposal from what was fenced is that it is narrowly scoped (SELECT-only), grant-gated (structurally, not just by policy), exercised once per explicit subscribe/re-sync action rather than continuously on every gameplay read, and leaves a permanent audit trail (§7) — a live-gameplay-resolution read across tenants would fail on all four of those properties at once, exercising the same boundary on every stat lookup forever, with a policy bug exploitable continuously and silently rather than at one loggable moment.

### 5. Copy powers gameplay; live mode is for browsing and diffing only

`mode = live` in `repository_subscription` exists for two purposes only: browsing a repository before deciding whether to subscribe to it in `frozen` mode, and diffing an already-frozen copy against its current source (§7). **It is never used for runtime stat or entity resolution in an actual campaign.** `mode = frozen` triggers a deep clone: walk the repository-tenant's reachable subgraph (its entities, `entity_prototype` edges, `stat_group`/`stat_definition`, `information`/`payload`), mint fresh ids in the subscriber's own tenant, and re-parent every `tenant_id`. Once complete, the subscriber's data is ordinary, self-contained tenant data — `v_effective_stat` resolves it with zero cross-tenant joins, indistinguishable from anything authored by hand.

Copying must happen in **dependency order**, and this has a real consequence for bridge repositories specifically: a bridge repository (e.g. `dnd_faerun`) is itself a subscriber, in `frozen` mode, of the repositories it bridges (`Faerûn`, `D&D 5e`) — it holds its **own local copies** of both before its own authors create any cross-referencing `entity_prototype` edge. This means no `entity_prototype` row is ever cross-tenant at rest, at any layer, including during bridge-repository authoring itself — which means bridge-repository authoring is never "live" against its own upstream dependencies. This is a deliberate choice, not an accepted gap: deciding how a setting's content and a system's mechanics fit together is curatorial, editorial work that should be reviewed and re-published deliberately when either dependency changes, not a live pass-through of whichever upstream edit landed most recently — the same reasoning, and the same answer, as why an end tenant doesn't get automatic upstream updates either (§7).

**Worked example** — a tenant subscribing to Faerûn under three possible systems: repositories `Faerûn` (content), `D&D 5e`/`Pathfinder`/`Shadowdark` (systems), `dnd_faerun` (a bridge, itself already holding local copies of `Faerûn` and `D&D 5e`, with its own authors having created e.g. an entity "Blackstaff (D&D 5e)" inheriting from both local copies, plus its own `EntityStat` overrides). A tenant subscribing to `Faerûn` + `D&D 5e` + `dnd_faerun` copies in dependency order: first `D&D 5e` (system prototypes and stat groups land with new ids), then `Faerûn` (Waterdeep, Elminster, Blackstaff land with new ids, system-agnostic), then `dnd_faerun` (its cross-repository edges and overrides get re-created using the subscriber's own now-local copies of both endpoints, resolved via the provenance table in §6). The tenant now holds "its own Blackstaff IS-A its own Staff(D&D5e)," entirely within its own tenant.

### 6. Deep clone by default, local additions always layered — never a fork

Freezing clones the **whole reachable prototype chain**, not just an entity's own local data with a live pointer back to shared definitions. A tenant's subsequent additions (a house-rule "Honor" stat) are ordinary new rows — a plain `INSERT` into the tenant's own `stat_definition`, or a new local prototype inheriting from the frozen copy — sitting beside the copied content, never editing it, never requiring anything a user would recognize as "forking." This resolves two requirements at once that initially looked like they pointed in different directions: it is what makes adding a house rule feel like an ordinary, everyday action rather than a special operation, and it is what makes a subscriber's own data durable against the source repository disappearing later (an author's account is deleted, a repository is unpublished, a table's connection is down) — once copied, a subscriber's data has zero runtime dependency on the source continuing to exist, for as long as the subscription has ever been frozen even once.

Per-source-table provenance makes "never editing the copy" verifiable rather than assumed:

- `repository_copy_link_entity(subscriber_entity_id, source_entity_id, source_repository_tenant_id, source_updated_at, copied_at)`
- `repository_copy_link_stat_group(subscriber_stat_group_id, source_stat_group_id, source_repository_tenant_id, source_updated_at, copied_at)`
- `repository_copy_link_stat_definition(subscriber_stat_definition_id, source_stat_definition_id, source_repository_tenant_id, source_updated_at, copied_at)`

(Real foreign keys into each real table — matching this schema's own existing preference for class-table precision over a polymorphic `(source_table, source_id)` pair with no enforceable FK, the same idiom `payload`'s own concrete tables already use.) A locally-authored row like Honor simply has no corresponding row in any of these tables — indistinguishable from copied content in every other respect, safe from re-sync by construction, not by convention. Whether `information`/`payload` need the same per-row provenance (for description/text-level re-sync granularity, not just stat-level) is an open v1-vs-v1.1 sizing question, not resolved here.

### 7. Re-sync is explicit, row-scoped, and never silent

Comparing a `repository_copy_link_*` row's recorded `source_updated_at` against the source row's current `updated_at` gives a cheap per-row staleness check. This must be **surfaced proactively** — through the same in-app notification/dashboard mechanism already used elsewhere in the product — rather than left for a GM to remember to go looking for; a perfectly safe mechanism nobody is ever told to use might as well not exist. Applying a specific update is always a deliberate, reviewable action against one specific row (a real diff of what changed, never a blanket "re-sync everything"), which per-row provenance makes a normal, scoped operation rather than a special case.

**Collisions are named as a real case, never resolved silently.** If an upstream repository later adds content that collides with a tenant's own existing addition (an upstream "Honor" stat landing on top of a tenant's own pre-existing "Honor"), the collision must be surfaced to the person applying the update as an explicit choice (rename / merge / skip) at the moment it's detected — never picked automatically, even by a definition of "safe" that seems obviously correct. A silent-but-sensible default is still a silent change to someone's game.

**Additions vs. corrections** are two different shapes of update worth naming distinctly, though both use the same mechanism: pulling a correction to a stat a tenant already has a copy of, versus pulling a stat that's new to a group the tenant already copied (no existing local row to update, a new one to add). The re-sync UX needs to handle both, not just the correction case.

### 8. Availability is three distinct things, not a boolean

- **Draft vs. published.** A repository-tenant has no content-relevant audience structure until explicitly published — content still being drafted with co-authors must never be visible to any subscriber or listing before that point.
- **Unlisted vs. discoverable.** This RFC scopes v1 to **unlisted-only**: a repository is subscribable only by tenants its owner explicitly grants access to. Public discoverability (a browsable marketplace) is explicitly out of scope (§Not in Scope) — it implies moderation, abuse-reporting, and trust signals nobody has designed, and naming that honestly now is better than backing into it unscoped.
- **The grant is a first-class record** — `repository_subscription` itself — not a boolean. It is created manually by the repository owner today, but structured so that *how* a grant gets created (manual approval, an invite link, a future payment step) is swappable later without redesigning the subscribe/copy mechanism underneath it.

### 9. Multiple prototype inheritance is the bridge mechanism

This operationalizes RFC 0001's own open question #3 rather than inventing something new: a bridge entity like "Blackstaff (D&D 5e)" is one ordinary entity with two prototype parents — a content-repository's entity (identity, lore, portrait) and a system-repository's entity (mechanical stat groups) — exactly RFC 0001's "system-agnostic prototype, system-specific variants inherit from it" idea, made concrete by having the bridge repository hold its own local copies of both (§5).

### 10. Knowledge on repository content is necessarily narrower than on live campaign content

Only the two campaign-independent visibility tiers — GM-only and public — are meaningful on a repository's own entities. Subset-visible and player-authored both presuppose real characters and real players, neither of which exist until a copy meets an actual campaign. This is not a gap in the knowledge system; it is the boundary of what a repository is for.

### 11. Cross-system stat coexistence is free at storage, real work at the presentation layer

Per [ADR 0079](../adr/0079-account-hub-roster-reuse-and-being-handoff.md), roster reuse is same-tenant, cross-campaign — the *same* entity linked into a second campaign's roster. Multiple `entity_prototype` inheritance and multiple `entity_stat_group` attachment already let one entity hold stat groups from two different subscribed systems simultaneously, with zero new schema; `v_effective_stat` resolves both without modification. What does **not** exist today: any way to filter a read down to "only the stats relevant to campaign X" — `campaign.game_system` (verified: a bare free-text column) has no structural link to any `stat_group`. Making that real is scoped, sequenced follow-up work (§Not in Scope), not a blocking prerequisite for the rest of this RFC, since the storage half already works unmodified. **Until that filtered view ships, the capability to roster the same character into a second campaign running a different system than its first must not be exposed** — without it, nothing stops a reused character's sheet from showing both systems' stats undifferentiated, which is a real, avoidable failure mode, not a cosmetic one. Same-system reuse, which already works today, is entirely unaffected by this restriction.

## Not in scope

- **A finer repository-author role.** Plain tenant `Membership` (§2) is what this RFC builds. A repository with multiple active co-authors may eventually want to distinguish a proposer from a publisher/maintainer — RFC 0018's still-unbuilt "repository author" role — but that need has not yet been demonstrated in practice and is deliberately left for its own follow-up rather than designed speculatively here.
- **The "facts" mechanism** (RFC 0001 open question #4). Copying a whole content-repository into a tenant makes its entities *available*, not automatically relevant to any one campaign's unfolding story — an NPC nobody's met is not meaningfully different, post-copy, from an NPC nobody's authored. This RFC's own copy mechanism makes that long-open gap newly urgent rather than hypothetical, but designing it is separate work this RFC deliberately does not attempt.
- **Public discoverability / a repository marketplace** (§8). Unlisted-and-granted only for v1.
- **Monetization or licensing of published content.** The subscription-grant record (§8) is deliberately structured so a payment step could plug into "how a grant gets created" later; no payment mechanism is designed here.
- **Migrating `campaign.game_system` to a real reference, and the filtered per-campaign stat view** (§11). Real, scoped follow-up, sequenced after this RFC's core mechanism ships — and required before cross-system roster reuse can be exposed, even though it does not block anything else in this document.
- **Per-row provenance for `information`/`payload`** (§6) — an open v1-vs-v1.1 sizing decision, not a design question, deliberately left for whoever picks up implementation to size against real re-sync granularity needs.
- **The isolation-test-suite extension and the DB-enforced `tenant.kind`/subscription-target checks (§2, §4) are required implementation scope, not optional hardening** — named here explicitly so they cannot be quietly dropped as "nice to have" once this becomes an ADR.

## Consequences

- Every future surface that lists, filters, or offers tenants for selection (a tenant switcher, campaign-creation flows, anything resembling "pick a tenant") must be aware of `tenant.kind` and correctly exclude repository-tenants, or they will leak into UI that assumes every tenant is a play tenant. This is real, ongoing surface area — not eliminated by this design, only concentrated at the product-UI layer rather than the query layer, which was the explicit trade this RFC makes.
- A repository-tenant's rows are still, mechanically, ordinary tenant-scoped data with a real `tenant_id` — just belonging to a tenant nobody plays a live game in. Every future feature built against `entity`/`stat_group`/etc. continues to work against repository-tenants unmodified; the cost of this design shows up in product surfaces (the point above), not in the domain model itself.
- Deep-clone-by-default means subscribing to a large repository is a real, potentially slow, bulk-copy operation, not an instant reference — performance of the copy walk at real repository sizes is unaddressed here and will need attention once real repositories exist to measure against.
- The activity log ([ADR 0063](../adr/0063-tenant-activity-log.md)/[ADR 0084](../adr/0084-activity-log-coverage-and-member-removal-notice.md)) should cover repository-tenant mutations through its existing mechanism — no second audit system is proposed or needed.
- This RFC deliberately reopens the same underlying primitive ("an authenticated read across a tenant RLS boundary") that an earlier, unscoped version of "cross-tenant repositories" was fenced off from building. The fence was against building that primitive undesigned; this document is the design the fence was waiting for — narrowly scoped, grant-gated at the data layer, SELECT-only, and audited — not a way around it.
