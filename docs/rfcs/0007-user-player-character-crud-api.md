# RFC: User, player, and character CRUD API

Status: proposed — builds on [RFC 0004](0004-user-membership-player-character-gm-read-api.md)'s read schemas and character table, and [RFC 0005](0005-item-and-item-instance-crud-api.md)'s write-API conventions; no schema changes of this RFC's own, but depends on RFC 0004's migration (the `character` table, `owner_player_id`'s move, `character_player`/`group_member`'s retargeted FKs) and [RFC 0010](0010-created-by-updated-by-attribution.md)'s (`created_by`/`updated_by` on `entity`/`membership`/`player`/`character`) having landed first

## Context

`app_user` is auto-provisioned by `get_current_user`'s upsert on first verified token ([ADR 0023](../adr/0023-authgear-token-verification.md)) — there is deliberately no "create a user" endpoint, since identity originates from Authgear, not this API ([ADR 0009](../adr/0009-identity-provider-authgear.md)). `membership`, `player`, `being`, and now `character` ([RFC 0004](0004-user-membership-player-character-gm-read-api.md)) all exist with no mutation path at all. [ADR 0010](../adr/0010-user-tenant-membership-model.md) named the sharpest open gap directly: "Invitation flow (how a GM adds a player to their tenant) is a real open question, not decided here" — still true. This RFC covers the three remaining pieces of the user's own ask: users (integrated with auth), players, and characters. Membership CRUD is included here rather than split out, since "who administers this tenant" is inseparable from "user" in exactly the way [RFC 0006](0006-campaign-crud-api.md) treats GM grants as inseparable from "campaign."

**Revised after [RFC 0004](0004-user-membership-player-character-gm-read-api.md) layered `character` under `being`.** That revision named two follow-ups for this RFC specifically: character creation must now also create the `Character` row, and `DELETE /characters/{id}` needs a real answer now that "demote to a plain `being`" and "destroy the whole entity" are two different, both-meaningful operations. Both are resolved below.

## Decision

### User: read and delete only — there is nothing else to write

`app_user` has exactly two data columns beyond its id and timestamps: `authgear_subject_id` (set once, at auto-provisioning, never again) and nothing else — no name, email, or avatar, which stay in Authgear by [ADR 0009](../adr/0009-identity-provider-authgear.md)'s explicit boundary. There is no `PATCH /me` in this RFC because there is no editable field to target; adding one would mean duplicating profile data this API has deliberately never stored.

| Method | Path | Auth | Response |
| --- | --- | --- | --- |
| DELETE | `/me` | any authenticated user, self only | `204` |

`DELETE /me` removes the caller's own `app_user` row. Cascades ([ADR 0018](../adr/0018-sqlalchemy-modeling-conventions.md)'s default, unchanged by anything here): every `Membership`, `Player`, `CampaignGm`, `TenantAdminCampaignOptOut` row this user held is deleted (the last renamed from `OrgaCampaignOptOut` by [RFC 0003](0003-tenant-campaign-read-api.md)/[RFC 0006](0006-campaign-crud-api.md), a stale reference fixed here too). Every `Character` they were the primary owner of (`owner_player_id`, living on `Character` since [RFC 0004](0004-user-membership-player-character-gm-read-api.md)'s revision, not `Being` anymore) loses that link (`SET NULL`) and survives as an ownerless character — the same "losing a player leaves the character, not deletes it" shape [ADR 0025](../adr/0025-character-being-and-ownership.md) already established, not a new rule. Guarded: `409 LastOwnerError` if the user is the sole `OWNER` `Membership` of any tenant — deleting themselves would leave that tenant with no one able to administer it at all, the same lockout `PATCH`/`DELETE /memberships` below also guards against. This endpoint only ever removes this API's own record; it does not and cannot revoke the underlying Authgear identity — a full account closure needs a separate, Authgear-side action, out of scope for an OIDC relying party ([ADR 0009](../adr/0009-identity-provider-authgear.md)'s own stated boundary).

**Also nulls every `created_by`/`updated_by` this user ever left behind** ([RFC 0010](0010-created-by-updated-by-attribution.md)) — `SET NULL` across `entity`, `campaign`, `membership`, `player`, `character`, `campaign_gm.created_by`, `tenant_admin_campaign_opt_out.created_by`, wherever this user was the actor, not just the rows they directly held a stake in above. Content and grants survive with anonymous attribution, the same "losing the actor doesn't delete the thing" shape as every cascade already described here — just one more column family it now applies to.

### Membership: invite, change role, revoke

| Method | Path | Auth | Body | Response |
| --- | --- | --- | --- | --- |
| POST | `/tenants/{tenant_id}/memberships` | `get_tenant_context` + `OWNER` only | `{user_id, role}` | `201 MembershipRosterEntryOut` |
| PATCH | `/tenants/{tenant_id}/memberships/{user_id}` | `get_tenant_context` + `OWNER` only | `{role}` | `200 MembershipRosterEntryOut` |
| DELETE | `/tenants/{tenant_id}/memberships/{user_id}` | `get_tenant_context` + (`OWNER` or self) | — | `204` |

Restricted to `OWNER`, not `ORGA` — granting/revoking administrative access is more sensitive than day-to-day tenant administration, a deliberate narrowing this RFC introduces (`403 MembershipManagementForbiddenError` for an `ORGA` caller who passes `get_tenant_context` but isn't `OWNER`). `PATCH`/`DELETE` both guard against removing the last `OWNER` (`409 LastOwnerError`) — the same structural concern `DELETE /me` above guards, expressed here for the "an owner demotes/removes someone else" path. `POST` sets `membership.created_by`/`updated_by` to the inviting owner ([RFC 0010](0010-created-by-updated-by-attribution.md)) — not the invitee, the same "who made this happen, not who it happened to" distinction [RFC 0006](0006-campaign-crud-api.md) draws for GM grants; `PATCH` updates `updated_by` to whichever owner changed the role.

**Invitation, honestly**: `POST /memberships` takes a `user_id`, not an email — this API has no email to look up (Authgear owns it, [ADR 0009](../adr/0009-identity-provider-authgear.md)). That means, as designed here, an owner can only invite someone who has already signed in at least once (so an `app_user` row already exists for them to reference). This is a real, worth-naming UX gap, not hidden — see Open questions.

### Player: join and leave a campaign

| Method | Path | Auth | Body | Response |
| --- | --- | --- | --- | --- |
| POST | `/tenants/{tenant_id}/campaigns/{campaign_id}/players` | `get_campaign_context` + `can_manage_campaign` | `{user_id}` | `201 PlayerOut` |
| DELETE | `/tenants/{tenant_id}/campaigns/{campaign_id}/players/{player_id}` | `get_campaign_context` + (`can_manage_campaign` or self) | — | `204` |

`can_manage_campaign` (defined in [RFC 0006](0006-campaign-crud-api.md)) gates adding a player — a GM building their own roster, or a tenant admin, not a self-service join, since there's no invite-link/visibility mechanism today that would make "anyone can add themselves to any campaign they can merely see" safe (see Open questions). Removal additionally allows the player leaving their own campaign voluntarily, without needing manage rights over it. No `PATCH`: a `Player` row has nothing mutable beyond the FKs that define its identity (`user_id`, `campaign_id`) — changing either is better modeled as delete-and-recreate than an in-place update of what the row *is*. `POST` sets `player.created_by`/`updated_by` to `CurrentUser.id` ([RFC 0010](0010-created-by-updated-by-attribution.md)) — always the managing GM/admin, since self-service joining doesn't exist yet (see Open questions); `updated_by` never diverges from `created_by` in practice, matching that RFC's own note that `player` gets the full pair for consistency despite having no update path.

### Character: create, promote, update, retire, and roster links

| Method | Path | Auth | Body | Response |
| --- | --- | --- | --- | --- |
| POST | `/tenants/{tenant_id}/characters` | self-or-managed (below) | `CharacterCreate` | `201 CharacterOut` |
| PUT | `/tenants/{tenant_id}/characters/{id}` | self-or-managed | `CharacterPromote` | `201`/`200 CharacterOut` |
| PATCH | `/tenants/{tenant_id}/characters/{id}` | self-or-managed | `CharacterUpdate` | `200 CharacterOut` |
| DELETE | `/tenants/{tenant_id}/characters/{id}` | self-or-managed | — | `204` |
| PUT | `/tenants/{tenant_id}/characters/{id}/players/{player_id}` | self-or-managed | — | `200 CharacterOut` |
| DELETE | `/tenants/{tenant_id}/characters/{id}/players/{player_id}` | self-or-managed | — | `200 CharacterOut` |

`CharacterCreate{name, owner_player_id: uuid.UUID | None = None, player_ids: list[uuid.UUID] = []}`. **Self-or-managed authorization, the "self" half applied uniformly across all five rows above**: allowed without further checks if `owner_player_id` (when given) and every id in `player_ids` are all `Player` rows the caller themselves holds — a player rolling their own PC needs no GM involvement, matching how a tabletop game actually works.

**The "managed" half is not one rule but three, split by what the write actually touches.** An earlier draft applied a single "every campaign the character's `Player` rows belong to" test uniformly across all five rows — disproportionate for two of them (a plain rename, or removing one roster link, would have needed sign-off from GMs of campaigns the write never touches at all) and inconsistent with [RFC 0005](0005-item-and-item-instance-crud-api.md)'s own reasoning for the structurally similar item-assignment case. Corrected here, resolving that RFC's Open questions entry too:

- **Writes that add, remove, or reassign a specific roster link** — `player_ids` on `CharacterCreate`, `owner_player_id` on `CharacterPromote`/`CharacterUpdate` (which also adds that id to the roster, per below), and the roster sub-resource `PUT`/`DELETE .../players/{player_id}` — need `can_manage_campaign` on **the specific campaign(s) of the `Player` row(s) actually being added, removed, or reassigned**, no more and no less: standing is needed exactly where the write acts. Creating (or promoting to) an ownerless NPC — `owner_player_id=None`, `player_ids=[]`, nothing to scope the check to at all — falls back to `can_manage_campaign` on *any* campaign in the tenant, mirroring [RFC 0005](0005-item-and-item-instance-crud-api.md)'s identical fallback for ownerless item-instance creation.
- **`PATCH` writes that touch only `name`** (`owner_player_id` unset, or set to its current value) need `can_manage_campaign` on **any one** of the character's current campaigns — the same "already uniformly visible everywhere it's rostered, so one GM's oversight is enough" reasoning [RFC 0005](0005-item-and-item-instance-crud-api.md) uses for assigning an item to someone else's character. A rename doesn't touch any roster link, so it doesn't need consent from every campaign that happens to share this character.
- **`DELETE` (demote)** needs `can_manage_campaign` on **every** campaign the character currently belongs to — the one operation here that actually, unilaterally ends its presence everywhere at once, rather than just in whichever single campaign the caller has standing in. See below.

`403` for a failed check either way, since the caller can already see enough to know what they're asking for — a plain `get_tenant_context`/`get_campaign_context` read-access check has already necessarily passed to get this far.

One transaction creates `Entity` + `Being` + **`Character`** ([RFC 0004](0004-user-membership-player-character-gm-read-api.md), `owner_player_id` now living there, not on `Being`) + one `CharacterPlayer` row per id in `player_ids`, referencing `character.entity_id` per that same RFC's retargeting (adding `owner_player_id` to that list automatically if it isn't already present — a primary owner who isn't also in the piloting roster would be a strange, easy-to-hit-by-accident state). `POST /characters` **always** creates the full `being`+`character` pair together — there is no way through this endpoint to create a bare `being` with no `character` row (an unnamed monster stub, a background NPC never worth individual tracking); that's a generic being-creation concern this RFC doesn't cover, the same boundary [RFC 0005](0005-item-and-item-instance-crud-api.md) draws around generic entity-attribute CRUD. Both `entity.created_by`/`updated_by` and `character.created_by`/`updated_by` ([RFC 0010](0010-created-by-updated-by-attribution.md)) are set to `CurrentUser.id` here — the two coincide at creation time, since nothing distinguishes "who made the being exist" from "who made it a character" until a later promotion might attach a `character` row to a `being` someone else made.

**`PUT /characters/{id}` promotes an existing `being` into a character — resolving this RFC's own previously-open question.** `{id}` is the target `being`'s entity id, already known to the caller (created by whatever means brought that bare `being` into existence in the first place — seed data, or a future generic being/entity CRUD this RFC still doesn't provide, per Not in scope below) — standard REST PUT-to-a-specific-URI semantics, deliberately different from `POST /characters`: POST always mints a brand-new id server-side, PUT always targets one the caller already has in hand. `CharacterPromote{owner_player_id: uuid.UUID | None = None}` — deliberately **no** `player_ids` list here, unlike `CharacterCreate`: the roster sub-resource endpoints below already own adding players one at a time, and reintroducing a wholesale list here would undercut the exact race-avoidance reasoning that kept `character_player` off `CharacterUpdate` in the first place. If `owner_player_id` is given, it's also added to the roster automatically, matching creation's own behavior.

**Idempotent, not one-shot**: calling it again on an already-promoted character just updates `owner_player_id` — the same field `PATCH` can already touch, and that overlap is fine, the same way PUT and PATCH routinely overlap in REST APIs generally. `201 CharacterOut` the first time (no `Character` row existed yet), `200 CharacterOut` on any later call (one already did) — standard convention for a PUT that may or may not be creating something, not a special rule invented here. `404 CharacterNotFoundError` if `{id}` isn't a `being` in this tenant at all — not treated as a different "wrong shape" condition, the same non-enumerable collapse every other not-found condition in this codebase already gets. Same self-or-managed authorization as create/update: a player promoting their own future PC needs no GM involvement; promoting someone else's `being` needs `can_manage_campaign` on the new owner's campaign specifically (the roster-link tier above), or on any campaign in the tenant if promoting to an ownerless NPC.

**This is exactly the case [RFC 0010](0010-created-by-updated-by-attribution.md)'s `character`/`entity` split exists for**: the first `PUT` sets `character.created_by`/`updated_by` to `CurrentUser.id` — the promoter — while `entity.created_by` keeps whatever it already was, from whenever the `being` was originally made, by whoever made it. A later repeat `PUT` (the idempotent-update case) only touches `character.updated_by`, never `entity`'s columns at all — promoting or re-promoting a character never implies anyone edited the underlying being.

`CharacterUpdate{name: str | None = None, owner_player_id: uuid.UUID | None = None}` — self-or-managed re-checked against the *new* `owner_player_id` if one is given, not just the character's current state; `owner_player_id` here means `character.owner_player_id` specifically. Which "managed" tier applies depends on what's actually changing: touching only `name` uses the any-one-current-campaign tier above; changing `owner_player_id` uses the specific-new-campaign tier, the same as `PUT`'s promotion case.

**`DELETE /characters/{id}` demotes — it deletes the `character` layer only, not the underlying `being`/`entity`.** Resolving [RFC 0004](0004-user-membership-player-character-gm-read-api.md)'s own open question: the path addresses "the character," and REST's own resource-addressing logic says that's what gets deleted — the `being`/`entity` underneath is a different resource, with its own (currently nonexistent) lifecycle, the same way deleting an `item_instance` doesn't touch the `item` prototype it inherits from. **Authorization uses the every-campaign tier above, not the any-one tier a rename gets**: demotion cascades every `CharacterPlayer`/`GroupMember` link away at once, ending the character's presence in every campaign it's currently rostered into simultaneously — the one write in this RFC where "any one GM's oversight" would let a single campaign's GM unilaterally end another GM's use of a shared character without their consent. Concretely: the `character` row is removed (`CharacterPlayer`/`GroupMember` rows referencing it cascade away, per [RFC 0004](0004-user-membership-player-character-gm-read-api.md)'s retargeted FKs — a demoted character isn't rostered or group-linked anymore, since neither mechanism can target a bare `being`); `Being`/`Entity` survive untouched, along with anything the character owned (`Ownership.owner_character_id` is a plain `FK → entity.id`, unaffected either way, [ADR 0025](../adr/0025-character-being-and-ownership.md)) or where it lives (`Containment`, likewise untouched) or any `Knowledge` it holds as a knower (`knower_entity_id` also `FK → entity.id`, not `being`/`character`-specific, [ADR 0028](../adr/0028-knowledge-and-group-membership.md)). **No additional data-integrity guard needed** (a separate question from the authorization tier above), deliberately contrasted with [RFC 0006](0006-campaign-crud-api.md)'s campaign-delete guard: demotion is inherently non-destructive to anything except the character-specific roster/group links, so there's nothing a guard would be protecting against. Fully destroying the underlying `being`/`entity` (and everything that cascades from *that*) isn't exposed by this endpoint at all — see Not in scope.

**Roster links as their own sub-resource**: `PUT/DELETE .../characters/{id}/players/{player_id}` add/remove one `CharacterPlayer` row at a time — the multi-valued counterpart to [RFC 0005](0005-item-and-item-instance-crud-api.md)'s singular owner/container sub-resources, adapted for a genuinely n:m relation (roster reuse, [ADR 0025](../adr/0025-character-being-and-ownership.md)) rather than a wholesale array replace on `CharacterUpdate`, for the same race-avoidance reason prototype editing was kept out of item `PATCH` in [RFC 0005](0005-item-and-item-instance-crud-api.md). Authorization uses the specific-campaign tier above, scoped to `{player_id}`'s own campaign — adding or removing this one link doesn't need consent from any other campaign this character happens to also be rostered into.

### Schemas

`ItemCreate`-style new modules: `schemas/players.py` (already created by [RFC 0004](0004-user-membership-player-character-gm-read-api.md)) gains nothing beyond what that RFC defined — `PlayerOut` is already the right create-response shape. `schemas/characters.py` (ditto) gains `CharacterCreate`, `CharacterPromote`, `CharacterUpdate`. `schemas/tenants.py` gains nothing new beyond [RFC 0004](0004-user-membership-player-character-gm-read-api.md)'s `MembershipRosterEntryOut`, reused as both read and write response — not `TenantMembershipOut`, which that RFC's own roster revision replaced outright with `TenantRosterEntryOut`'s discriminated union before this RFC was drafted; a stale name never actually defined anywhere, fixed here.

## Not in scope

**Campaign and GM-grant mutation** — [RFC 0006](0006-campaign-crud-api.md).

**Character "retirement" as a soft-delete alternative.** [docs/domain/client-views.md](../domain/client-views.md)'s own "future direction" section names a ledger-of-ownership/ownership-provenance idea explicitly as *not* being built yet; a status flag distinguishing "retired" from "deleted" would be a natural extension of that same not-yet-scoped direction, not something this RFC adds speculatively. Distinct from `DELETE`'s new demote behavior above: retirement would mean *still a character, just inactive*, where demotion means *not a character at all anymore*.

**Per-player character caps or other game-balance rules** — nothing asked for this, and it would vary per table/game system in ways this API has no mechanism to express yet.

**Fully destroying a `being`/`entity`, and creating a bare `being` with no `character` row.** Neither is exposed anywhere in this RFC — both are generic being/entity-lifecycle concerns, not character-specific ones, and belong to whatever future RFC covers generic entity CRUD (the same boundary [RFC 0005](0005-item-and-item-instance-crud-api.md) already draws for items). `PUT /characters/{id}` (above) *promotes* an existing `being`, but doesn't create one from nothing — a GM who wants a truly disposable, never-to-be-a-character NPC still has no API path to create just that today, same as before this revision — not a regression, just an unaddressed gap this RFC doesn't newly create or newly close.

## Open questions

**Invitation UX.** `POST /memberships`/`POST .../players` both require the invitee's `user_id` already existing, which in practice means "has signed in at least once." A friendlier email-based invite would need either apps/api to start caching email (a real, deliberate widening of [ADR 0009](../adr/0009-identity-provider-authgear.md)'s "email stays in Authgear" boundary) or a call into Authgear's own admin API to resolve one — neither designed here, both real future work. Shipped as-is, this RFC's invitation flow is functional but clunky: an inviter needs the invitee's internal id, not just something they already know like an email or Discord handle.

**Self-service campaign joining.** Today, only a manager can add a player — there's no "request to join" or invite-link flow a plain user can act on themselves. A `Campaign.is_joinable` flag or a separate invite-token mechanism could enable that later without redesigning anything decided here; not built now because nothing about visibility/discovery of joinable campaigns has been designed either (see [RFC 0003](0003-tenant-campaign-read-api.md)'s own open question about campaign-list visibility).

**Reassigning a character to someone else's player used to need `can_manage_campaign` on *every* campaign that character's `Player` rows belong to, while [RFC 0005](0005-item-and-item-instance-crud-api.md) required only *one* for its own analogous "give someone else's character an item" case.** **Resolved** — the two operations were never quite analogous. Reassigning a roster link is a concrete action inside specific campaigns and needs standing there specifically (the roster-link tier in Decision above); a plain rename has no cross-campaign effect at all (the any-one tier, matching RFC 0005's own reasoning exactly); only a full demote — ending the character's presence everywhere at once — actually warrants consent from every campaign it's in. See Decision above for the three-way split this RFC now uses in place of the single blanket rule.

## Consequences

- No migration of this RFC's own — but it now depends on [RFC 0004](0004-user-membership-player-character-gm-read-api.md)'s migration (`character`, `owner_player_id`'s move off `being`, `character_player`/`group_member`'s retargeted FKs) and [RFC 0010](0010-created-by-updated-by-attribution.md)'s (`created_by`/`updated_by` on `entity`/`membership`/`player`/`character`) both having landed first, unlike this RFC's first draft, which depended on `app_user`/`membership`/`player`/`being`/`character_player` needing nothing further.
- Every write path in this RFC (membership invite/role-change, player add, character create/promote/update) needs to actually set `created_by`/`updated_by` from `CurrentUser.id` — a small, mechanical addition per route, tracked in [RFC 0010](0010-created-by-updated-by-attribution.md)'s own consequences too so it isn't only remembered here.
- `LastOwnerError`/`MembershipManagementForbiddenError` join `exceptions.py`'s roster, following [RFC 0005](0005-item-and-item-instance-crud-api.md)'s subclassing convention.
- `DELETE /me` is the first endpoint in this codebase where a user can remove their own top-level identity row — worth a deliberate, explicit test proving the last-owner guard actually fires, not just the happy-path cascade.
- The self-or-managed authorization shape introduced here for characters (self-service within your own resources, manager override beyond them) is a pattern worth reusing if a future RFC ever needs the same "you can always act on your own stuff" carve-out elsewhere.
- `DELETE /characters/{id}`'s demote-not-destroy resolution means this RFC's own test suite needs a case proving the underlying `being`/`entity` (and anything it owns, contains, or knows) survives a character delete — the opposite of what "delete" usually proves, so worth calling out explicitly rather than assuming the obvious cascade test covers it.
- `PUT /characters/{id}`'s two-status-code behavior (`201` first call, `200` on a repeat) needs its own explicit test on each branch — easy to get backwards or leave only one covered, since most of this codebase's existing endpoints return exactly one status code per route, not a conditional one.
- Character creation writes through `Player.owned_characters` (renamed from `owned_beings` by [RFC 0004](0004-user-membership-player-character-gm-read-api.md)), not the old relationship name — anything implementing this RFC against a checkout that still has the old name needs that revision applied first.
- The three-way "managed" authorization split above needs its own test matrix, not just one managed-tier test per endpoint: the roster-link tier (scoped to one specific campaign, including the ownerless any-campaign fallback), the any-one-current-campaign tier (`PATCH` rename), and the every-campaign tier (`DELETE`) are three genuinely different queries against three different sets of campaigns — easy to accidentally collapse back into one shared helper that quietly re-broadens or narrows one of them.
