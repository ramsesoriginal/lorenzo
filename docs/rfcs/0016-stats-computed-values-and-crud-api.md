# RFC: Stats — enum values, computed stats, tags, and a real read/write API

Status: proposed; sub-slices 1 to 3 accepted by [ADR 0103](../adr/0103-stat-tags-enum-values-and-mandatory-groups.md), 4 and 5 by [ADR 0104](../adr/0104-computed-stats.md)

## Context

[ADR 0014](../adr/0014-stats.md) built `stat_group`/`stat_definition`/`entity_stat`/`entity_stat_group` as a deliberately narrow proof-of-concept: `value_type` is `int`/`text`/`float`/`bool` only, no computed/derived values, nothing beyond direct storage. [ADR 0037](../adr/0037-effective-stat-resolution.md)/[ADR 0039](../adr/0039-generic-effective-stat-view.md) built the inheritance-resolution mechanism — `v_effective_stat`'s recursive CTE, entity-generic, "closest prototype hop wins outright" — but it only ever resolves *stored* values; nothing computed or derived.

Working through what "a stat" is actually meant to cover in practice surfaced four real categories, three of which need no new mechanism at all:

- **Tags** (`consumable`, `wearable`, `is_metal`) — already free: a bool `stat_definition` set `true`. No gap here beyond ergonomic write endpoints (see Decision).
- **Counters/gauges** (charges, capacity) — after discussion, deliberately **not** a new concept: plain `int` `stat_definition`s by convention (`charges_current`, `charges_max` as two ordinary stats), no first-class current/max pairing. Named explicitly here so it isn't silently assumed built later.
- **Enum-constrained values** (`rarity`, `class`, `sourcebook`) — a real gap: `text` would hold `"rare"` but enforces nothing about the allowed set, unlike `stat_definition.value_type`'s other three members.
- **Computed/derived stats** (unit conversion, multipliers, attribute-score curves, classification, thresholds) — the real new mechanism this RFC exists for.

The computed-stat *representation* question — how a formula actually gets stored and evaluated safely, given campaign GMs (not developers) author these through a future client app, evaluated server-side on every read — was resolved through a structured, four-position adversarial debate (a general JSON op-tree, a text DSL, curated first-class "computed stat kind" tables, and a small curated JSON op-tree), each independently researched, cross-examined, and rebutted. **Curated first-class kind tables won**, for three compounding reasons: it's the only option with zero interpreter anywhere in the system (every "formula" is a parameterized call into reviewed application code, not parsed or tree-walked user input) — the right fit given GM-authored, server-evaluated, multi-tenant formulas; it reuses this codebase's own already-trusted class-table-inheritance idiom (`entity`/`item`/`being`, and `payload`/`payload_entity` from [RFC 0015](0015-information-metadata-shape.md)) rather than introducing a new kind of component; and its apparent composability ceiling — "what about combining two things no single kind covers?" — is answered by **chaining through named intermediate stats** rather than nested expressions, which is arguably the better domain fit anyway: TTRPG character sheets already present derived values this way ("proficiency bonus," "strength modifier"), never as anonymous nested formulas.

Two things this RFC deliberately does **not** attempt, narrowed during the same conversation rather than silently assumed:

- **Game-system scoping** ("this stat is generic, that one is D&D-specific") — stays out of scope; stats remain system-agnostic for this slice. A concrete idea exists for this later, not designed here.
- **Cross-entity aggregation** (e.g. "sum of everything in this container's weight") — computed stats only ever reference *other stats on the same entity*. Every worked example and the whole resolution/dependency-ordering design below assumes this.

Resolution itself is unchanged from what [ADR 0037](../adr/0037-effective-stat-resolution.md) already decided: a computed contribution competes at whatever prototype hop it sits, via the exact same "closest hop wins outright" rule as a direct value — no layered modifier-stacking, considered and explicitly rejected as unneeded complexity for what this project actually needs right now.

## Decision

1. **`stat_group.mandatory`** (boolean, default `false`) — purely advisory, not enforced by anything. Lets a client render an "empty" field (see decision 8) more insistently when it belongs to a mandatory group, without the database ever checking it's actually been filled in.
2. **`value_type` gains a fifth member, `enum`**, backed by a new `stat_definition_enum_value(stat_definition_id, tenant_id, value, sort_order)` table — `UNIQUE(stat_definition_id, value)`, same tenant-scoping/RLS convention every table in this schema already follows. `sort_order` is a plain display hint (a client rendering a `rarity` dropdown wants `common` before `legendary`), not itself uniquely constrained.
3. **Computed stats: a shared `computed_stat(entity_id, stat_definition_id, tenant_id, ...)` base table**, composite PK matching `entity_stat`'s own `(entity_id, stat_definition_id)` shape exactly — a computed contribution is addressed identically to a direct one, since it competes in the same resolution walk at the same hop. No kind column, mirroring `payload`'s own precedent: which concrete table has a matching row tells you the kind. Two concrete kinds cover every motivating example from the debate:
   - **`computed_stat_linear`** — a source stat, a multiplier, an offset, and an explicit `round_mode` (`none`/`floor`/`ceil`/`round`/`truncate`) — covers unit conversion (`height_cm = height_inch × 2.54`), simple multipliers (`effective_ac = material_ac × 1.5`), and attribute-score-style curves (`strength_modifier = floor((strength − 10) / 2)`). The explicit `round_mode` matters: `floor` and `truncate` disagree on negative-odd inputs (`floor((9-10)/2) = -1`, truncation gives `0` — the wrong D&D modifier), a real correctness bug the debate itself surfaced and this RFC fixes by naming the parameter rather than leaving it implicit.
   - **`computed_stat_comparison`** — a left stat, a comparator, a right side (another stat or a constant), and true/false result values — covers classification (`weight_class = weight > 50 ? "heavy" : "light"`) and derived booleans (`is_overloaded = carried_weight > carry_capacity`).

   Composing beyond what one kind covers (e.g. "scale, then classify") happens by **chaining**: define a named intermediate computed stat (`base_scaled` via `computed_stat_linear`), then reference it from another kind's own source-stat column — not by nesting expressions inside one row.
4. **Resolution integration**: `v_effective_stat`'s recursive CTE ([ADR 0037](../adr/0037-effective-stat-resolution.md)/[ADR 0039](../adr/0039-generic-effective-stat-view.md)) needs to consider `computed_stat` rows, not just `entity_stat` rows, when deciding what wins at each hop. When a `computed_stat` row wins, a Python-side pass evaluates its formula against that entity's already-resolved stat bundle — the already-accepted cross-cutting fact from the debate: arbitrary formula evaluation doesn't belong inside a live, uncached recursive CTE.
5. **Dependency ordering and cycle detection over formula references** — a second, independent graph from `entity_prototype`'s own inheritance graph (already cycle-rejected, [ADR 0015](../adr/0015-entity-prototype.md)). A computed stat referencing another computed stat (same entity only, per Context) needs topological evaluation order and a cycle check of its own; conflating the two graphs would be a bug.
6. **A unified stat bundle endpoint**: `GET`/`PATCH /tenants/{tenant_id}/entities/{entity_id}/stats` — every `stat_definition` reachable through the entity's acquired `stat_group`s (direct ∪ computed ∪ inherited ∪ empty), each field annotated with where its value came from (`direct`/`computed`/`inherited`/`empty`), filterable by `stat_group`. One endpoint, not the two originally proposed (a "values" bundle and a separately-fetched "computed" bundle) — a client rendering a character sheet wants all of this together, not stitched from two calls. `PATCH` follows [JSON Merge Patch](https://www.rfc-editor.org/rfc/rfc7396) semantics: an omitted field is untouched, an explicit `null` clears this entity's own direct override (reverting to whatever the prototype chain/computation would otherwise resolve to) — no separate whole-resource `POST`/`DELETE`, since "the bundle" always conceptually exists the moment the entity does. Concurrency is checked **per field inside one transaction**, not via a single bundle-wide `If-Match` — a token covering dozens of rows, some inherited from ancestor entities that can change independently, would go stale from unrelated writes constantly.
7. **Tag endpoints**: `PUT`/`PATCH`/`DELETE /tenants/{tenant_id}/entities/{entity_id}/tags/{stat_definition_id}` — three states, not two: `PUT` sets `true` (and auto-acquires the stat's `stat_group` via `entity_stat_group` if not already acquired, closing [ADR 0037](../adr/0037-effective-stat-resolution.md)'s own named "setting an unacquired stat is possible and unenforced" gap for this one common case), a second verb sets explicit `false` (an affirmative override, not silence — e.g. a door built on the `wood` prototype but since replaced with metal), and `DELETE` clears the entity's own row entirely, reverting to inherited resolution.
8. **Computed-stat formula authoring**: `POST /tenants/{tenant_id}/entities/{entity_id}/computed-stats` (a `kind`-discriminated body: `linear`/`comparison`) creates the `stat_definition` (if new, by name) *and* the `computed_stat_*` row atomically, mirroring `create_information`'s existing atomic multi-table creation ([ADR 0038](../adr/0038-information-payload-knowledge-crud-api.md)); `PATCH`/`DELETE` edit or remove one. **Authorization is tenant-admin tier**, the same bar `stat_group`/`stat_definition` already use ([ADR 0037](../adr/0037-effective-stat-resolution.md)) — a formula is exactly that kind of shared, defined-once, built-on-top-of-by-everything-else concern, not a self-or-managed one. Deliberately a placeholder, not a final answer: a future "repository author" role is expected to eventually own this instead, with a tenant admin subscribing to (copying from) a repository rather than authoring from scratch — that role doesn't exist yet, tenant-admin is what this RFC actually builds. Three more pieces, load-bearing for a non-technical author, not optional polish:
   - **Cycle/dependency validation at write time** — reject a formula whose source doesn't exist yet, or that would create a circular reference (required by decision 5, not a separate feature).
   - **A dry-run/preview** — evaluate a formula (saved or not-yet-saved) against a specific real entity, returning the result before committing. The actual answer to "a filled-in form is valid, but is it *right*."
   - **A reverse-dependency lookup** — "what else references this stat" — before editing or deleting one something else depends on, mirroring [ADR 0073](../adr/0073-item-prototype-graph-inspection-and-bulk-editing.md)'s own prototype-graph reverse-lookup precedent, just applied to formula dependencies instead of inheritance.

   **No batch/multi-step "create a whole chain in one call" endpoint** — deliberately rejected. Nothing about a form-based authoring UI needs it, this API has no batch-endpoint precedent anywhere else, and it's exactly the kind of unrequested complexity [AGENTS.md](../../AGENTS.md) already steers away from.

### Sub-slices, smallest first

1. `stat_group.mandatory` (decision 1 — trivial, standalone).
2. Tag endpoints (decision 7 — needs only what already exists: `entity_stat`, `entity_stat_group`, the existing single-stat write path).
3. `value_type=enum` + `stat_definition_enum_value` (decision 2 — independent new schema, no dependency on computed stats).
4. Computed stats' core mechanism: `computed_stat` + `computed_stat_linear`/`computed_stat_comparison` + resolution-walk integration + the `round_mode` fix (decisions 3, 4).
5. Computed stats' QoL surface: cycle/dependency validation, dry-run preview, reverse-dependency lookup (decisions 5, 8 — needs slice 4 first).
6. The unified stat bundle endpoint (decision 6 — deliberately last; it's most valuable once direct, computed, and enum values all actually exist to show).

### What this RFC deliberately does not decide

- **Exact column shapes** for `computed_stat_linear`/`computed_stat_comparison` (the precise `round_mode` enum values, whether a comparison's right-hand side is a typed union of columns or something else) — ADR-level detail.
- **Whether more computed-stat kinds are needed beyond `linear`/`comparison`** — grow via migration as a real, concrete need appears, matching option C's own governance discipline from the debate, not speculatively here.
- **Game-system scoping's actual mechanism** — named in Context as explicitly out of scope for this slice, not forgotten.
- **Cross-entity aggregation** — named in Context as explicitly out of scope; every kind here reads only the same entity's own resolved stats.
- **The unified bundle endpoint's exact JSON field names** and whether `If-Match` is dropped entirely vs. kept per-field internally — the per-field *approach* is decided (decision 6), the wire-level detail isn't.
- **Escalating to a small curated JSON op-tree (the debate's "option D")** if chaining-via-named-stats proves unwieldy in real usage (e.g. too many throwaway intermediate stats for genuinely one-off inline math) — not decided now, but the debate that would resolve it already happened and should be referenced, not re-litigated, if that day comes.

## Consequences

- `v_effective_stat`'s resolution CTE needs to check `computed_stat` rows alongside `entity_stat` rows at every hop — a real, if contained, change to an already-live view, not a purely additive one.
- Computed-value evaluation moves partially out of SQL and into application code: a post-resolution Python pass becomes load-bearing for correctness whenever an entity carries any computed stat, not just a convenience layer.
- Two independent cycle checks now exist over two different graphs — `entity_prototype`'s inheritance graph (already enforced) and computed-stat formula dependencies (new) — conflating them anywhere in the implementation would be a real bug, not a style issue.
- The unified stat bundle endpoint is a new, additive read/write surface — it doesn't replace or change the existing single-stat `PUT` ([ADR 0037](../adr/0037-effective-stat-resolution.md)) or the existing `effective_stats`-based read paths (`GET /entities/{id}`, `ItemOut`/`ItemInstanceOut`'s 8 named columns), which stay exactly as they are.
- `stat_definition_enum_value` adds a real, tenant-authored vocabulary layer parallel to `stat_group`/`stat_definition`'s own naming — same `UNIQUE`/RLS conventions as everything else in this schema, no new pattern introduced.
- Computed-stat evaluation is live and uncached, same as `v_effective_stat`'s own resolution ([ADR 0039](../adr/0039-generic-effective-stat-view.md)) — real materialization/caching is a genuine, known future need, not solved by this RFC. Named here explicitly so it isn't mistaken for a closed question.
