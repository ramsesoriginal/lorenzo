# RFCs

For proposals that aren't decided yet — bigger than an ADR captures, or genuinely open questions. An RFC becomes one or more ADRs once decided (or gets dropped).

To start one: copy an [ADR](../adr/0000-template.md)'s structure but title it "RFC: \<question\>" and leave Decision open until there's consensus.

- [0001 - Core domain data model (entity/component architecture)](0001-core-domain-data-model.md) — proposed, pending the knowledge/redaction and multi-game-system questions; tenancy-split resolved for every table the items slice uses, narrowed to just the not-yet-designed repository-reference mechanism
- [0002 - Campaign, player, and character model](0002-campaign-player-character-model.md) — accepted, landed in full across ADR 0021-0026; revises ADR 0010's tenant definition
- [0003 - Tenant and campaign read REST API](0003-tenant-campaign-read-api.md) — accepted, landed in [ADR 0030](../adr/0030-tenant-campaign-read-api.md)
- [0004 - User, membership, player, character, and GM read REST API](0004-user-membership-player-character-gm-read-api.md) — accepted, landed in [ADR 0031](../adr/0031-character-table-and-read-api.md)
- [0005 - Item and item-instance CRUD API](0005-item-and-item-instance-crud-api.md) — accepted, landed in [ADR 0032](../adr/0032-item-and-item-instance-crud-api.md); also introduces the shared `entity_access.py` reachability walk (for RFC 0009) and pulls `campaign_access.can_manage_campaign` forward from RFC 0006; revises item-instance *read* authorization to `is_tenant_participant` too, a gap this RFC's text didn't itself cover but the milestone required
- [0006 - Campaign CRUD API](0006-campaign-crud-api.md) — accepted, landed in [ADR 0034](../adr/0034-campaign-crud-api.md); consumes `campaign_access.can_manage_campaign` and its siblings exactly as RFC 0005/ADR 0032 pulled them forward, rather than defining them
- [0007 - User, player, and character CRUD API](0007-user-player-character-crud-api.md) — accepted, landed in [ADR 0036](../adr/0036-user-player-character-crud-api.md); resolves ADR 0010's invitation-flow question with a known limitation; `DELETE /characters/{id}` demotes rather than destroys, `PUT /characters/{id}` promotes an existing being the other way; character authorization's "managed" tier split three ways (roster-link changes, plain edits, demote), consuming a new `campaign_access.can_manage_every_campaign` for both the roster-link and every-campaign tiers
- [0008 - Effective stat resolution over the prototype graph](0008-effective-stat-resolution.md) — accepted, landed in [ADR 0037](../adr/0037-effective-stat-resolution.md); resolves the mechanism (a recursive CTE in `v_item`/`v_item_instance`) and the `stat_group.priority` tie-break's own precise meaning, neither pinned down by this RFC's text
- [0009 - Campaign-scoped GM visibility](0009-campaign-scoped-gm-visibility.md) — accepted, landed in [ADR 0035](../adr/0035-campaign-scoped-gm-visibility.md); revises `information_visibility.py`'s ORGA-only bypass so a campaign's own GM sees GM-only secrets without needing tenant-wide Membership, reusing ADR 0032's `entity_access.reachable_entity_ids`
- [0010 - Attribution — created_by/updated_by](0010-created-by-updated-by-attribution.md) — accepted, landed in [ADR 0029](../adr/0029-attribution-created-by-updated-by.md); `entity`'s pair is built, the rest land incrementally with each table's own CRUD slice per that ADR's phased-implementation table
- [0011 - Information, payload, and knowledge CRUD API](0011-information-payload-knowledge-crud-api.md) — accepted, landed in [ADR 0038](../adr/0038-information-payload-knowledge-crud-api.md); scoped to description payloads and self-or-managed authorization uniformly across every visibility tier - the finer per-tier model this RFC named but didn't resolve stays open
- [0012 - Tenant creation and update API](0012-tenant-creation-and-update-api.md) — accepted, landed in [ADR 0033](../adr/0033-tenant-creation-and-update-api.md); gated by an Authgear-assigned `tenant-creator` role (not "any authenticated user" — revised), picking up ADR 0010's anticipated platform-admin need; resolves RFC 0003's deferred slug-generation/collision question; deletion explicitly excluded pending ADR 0018's own flagged cascade concern
- [0013 - `apps/account-hub`: a user's own account surface](0013-account-hub-app.md) — proposed; scopes a new static web app (profile, notifications, tenant/campaign listing, character CRUD for players, being CRUD for GMs) forking `apps/inventory-web`'s Astro/Authgear pattern, chosen via a structured multi-option debate over mobile/desktop/Discord-bot/conversational alternatives
- [0014 - `apps/account-hub`: tenant/campaign administration and roster reuse](0014-account-hub-tenant-admin-and-roster-management.md) — proposed; surfaced by manual testing of RFC 0013's Characters slice - campaign creation, GM assign/revoke, player invites, and character/being roster reuse across campaigns in a tenant, all against already-built `apps/api` surface
- [0015 - `information`/`payload` — a generic metadata container: types, ordering, and the rest of the CRUD surface](0015-information-metadata-shape.md) — proposed; the RFC 0011 sequel, picking up the gaps ADR 0017/0028/0038 each named and deferred (per-type singleton uniqueness, payload ordering, editing/deletion, a real collection endpoint, player-knowers on the write side) plus a fifth payload kind and a generalized `entity_slug` table — originally numbered 0014, renumbered on merge into `main`: `main` had independently claimed 0014 for account-hub's own tenant/campaign-admin RFC in the meantime
- [0016 - Stats: enum values, computed stats, tags, and a real read/write API](0016-stats-computed-values-and-crud-api.md) — proposed; adds a 5th `value_type` (`enum`), a curated (no-expression-language) computed-stat mechanism chosen via a structured four-position debate, ergonomic tag endpoints, and a unified stat bundle endpoint replacing the two originally-separate "values" and "computed" bundle ideas
- [0017 - `apps/account-hub`: roster view, tenant admin, and notification sending](0017-account-hub-roster-tenant-admin-and-notifications.md) — proposed; numbered past 0015/0016, already claimed by a different open PR at the time this was written; campaign roster view, being search, leave-a-campaign, tenant creation, tenant-level membership management + bulk invite, activity log, and notification sending/sent - all against already-built `apps/api` surface, including a richer roster endpoint that also fixes a raw-`user_id`-only limitation named in ADR 0076/0079
- [0018 - `entity_template` — a curated, ordered composite of information and stats](0018-entity-template.md) — proposed; a first step toward game systems as a modeled concept - a tenant-scoped, named, ordered projection (concrete-kind-and-prototype-ancestry filter, information/stat-group slots) an entity can be read through; read-only for this slice, composite writes and cross-tenant portability (RFC 0001's still-open "repository" question) both deliberately deferred
- [0019 - Shareable, expiring campaign invite links](0019-shareable-campaign-invite-links.md) — proposed; hashed 256-bit tokens, required expiry and use cap, player-only grant, and an explicit abuse-protection section (no rate limiter exists; recommends an edge rule plus an in-process backstop)
