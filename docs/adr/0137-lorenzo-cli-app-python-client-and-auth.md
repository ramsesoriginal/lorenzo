# 0137 - `apps/cli`: a Python CLI, its generated client, and its auth

Status: accepted

Slice 1 of [RFC 0025](../rfcs/0025-lorenzo-cli-mpmb-item-importer.md) (R2 of its cross-persona review, and §1).

## Context

RFC 0025 names an `apps/cli` and defers its scaffolding to implementation. The review settled the stack in R2 but left the moving parts to be recorded here: how the app is laid out, how it talks to `apps/api`, and how it gets a token. Two facts shape it:

- `apps/api` is the only Python app. `apps/loot-bot`, `apps/inventory-web` and `apps/account-hub` are TypeScript and share `packages/api-client` ([ADR 0122](0122-api-client-package.md)), which a Python CLI can't use without putting Node on a game master's machine.
- The OpenAPI document is git-ignored and generated by `apps/api/scripts/dump_openapi_schema.py`, with no database needed.

## Decision

### The app

`apps/cli` is a standalone uv project like `apps/api`: `src/lorenzo_cli`, hatchling, Python 3.14, `uv.lock` committed, ruff (`line-length = 100`), strict mypy, pytest. It installs a `lorenzo` console script. Its `mise.toml` has the contract every app has (`dev`, `lint`, `format`, `test`, `build`) plus `lock` and `check-schema`. There is no Dockerfile and no deploy workflow: it is installed, not deployed.

The command line uses `typer` (which brings `rich` for the output the RFC asks for). Commands are added by the slices that need them. This slice has `login`, `logout` and `tenant show` (which reads a tenant by id or slug, and so is the first call through the client); `seed`, `plan` and `apply` come with the later slices.

### The client

- **Models are generated** from the dumped OpenAPI document by `datamodel-code-generator`, committed, and pinned, so a schema change shows up as a diff. `openapi-python-client` is rejected: it silently dropped `ComputedStatOut` and two endpoints while reporting success.
- **Transport is hand-written**, about 200 lines over `httpx`, and mirrors `packages/api-client`:
  - One `LorenzoApiError` carrying the status and the `application/problem+json` body, its message taken from `detail`, then `title`, then `Request failed (N)`.
  - `Authorization: Bearer …`, and `If-Match` from an entity's ETag. A `412` is surfaced as "re-read and re-plan"; a `401` refreshes the token once.
  - Only `GET`, `PUT` and `DELETE` are retried, never `POST`, since there is no idempotency key.
- **An `OPS` table** maps `operationId` to `(method, path, request model, response model)`. A test checks every entry against the dumped schema, which gives the path-level safety the TypeScript client gets from its generated types.
- **Drift.** `mise run check-schema` in `apps/cli` dumps the schema, regenerates the models, and runs `git diff --exit-code`. It is added to the existing `client-drift` job and to `ci-summary`.

The client stays inside `apps/cli`. A shared `packages/api-client-py` waits for a second Python consumer (no `utils`-style extraction ahead of need). It does not import `lorenzo_api.schemas`, which would couple the CLI to server internals.

### Auth

The CLI is run by a person with their own token. Unattended use is out of scope.

- `LORENZO_TOKEN` or `--token-stdin` supply a token directly. This unblocks development (feed it from `apps/api/scripts/get_dev_token.py`) and scripts.
- A stored login (issuer, client id, access token, refresh token, expiry) lives in a `0600` file under `$XDG_CONFIG_HOME/lorenzo/`, created private from the start. The access token is renewed with the refresh token shortly before it expires and once after a `401`. Storing it in the OS keychain (the `keyring` package) is left for when someone needs it; a headless WSL has no keychain to talk to.
- The order of use is `--token-stdin`, then `LORENZO_TOKEN`, then the stored login.
- There is no default API URL: `LORENZO_API_URL` or `--api-url` must name it, so a token never goes to a host nobody chose.
- `login` runs the authorization code flow with PKCE against a **new public Authgear client** on a fixed loopback port, asking for `openid offline_access`. `login --no-browser` prints the URL and reads the redirected URL back, which covers WSL and SSH. Authgear has no device authorization grant.
- Registering that client is an operations step, not code, and it is unverified whether Authgear accepts a secret-less native client on a fixed loopback port. Until it is registered, `login` fails with a message saying so; nothing else depends on it.
  - *Addendum, 2026-10-03: the client is registered, as a Single Page Application (Authgear's public, PKCE type), and accepts `http://127.0.0.1:8766`, `:8767` and `:8768` `/callback`. The Native type wasn't needed. Whether it is given a refresh token, and for how long, is what the first real `lorenzo login` settles.*

## Consequences

- One more app to lint, test, release, and keep in Dependabot: `apps/cli` is added to the root `mise.toml`, `release-please`, `dependabot.yml`, the pre-commit hooks, the `release.yml` lockfile step, and the required-status ruleset (`test (apps/cli)`).
- Two generated clients now describe one API. The `check-schema` job makes drift a CI failure rather than a surprise, at the price of a second regeneration step whenever `apps/api`'s schema changes.
- `typer` and `httpx` are new runtime dependencies. The generated models add `pydantic`, which `apps/api` already uses.
- The design of the JS host ([RFC 0025 R1](../rfcs/0025-lorenzo-cli-mpmb-item-importer.md#r1-the-js-host-embedded-v8-in-a-token-free-worker)) is recorded in its own ADR; this one only fixes that the worker is a subprocess of `apps/cli`.
