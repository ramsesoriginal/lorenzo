# 0053 - loot-bot: HTTP interactions transport and Cloud Run deployment

Status: accepted

## Context

`apps/loot-bot` has never been deployed anywhere. Its own README recorded the open question plainly: "Deployment: Not yet decided. A persistent Discord gateway connection doesn't fit Cloud Run's scale-to-zero model the way `apps/api` does." Today the bot is a Gateway bot: `src/index.ts` opens a discord.js `Client({ intents: [GatewayIntentBits.Guilds] })` and calls `client.login()`, and `src/commands/index.ts`'s dispatcher only ever handles `Events.InteractionCreate` — no message content, presence, or voice usage anywhere in the codebase.

Four concrete deployment options were compared - Google Compute Engine's `e2-micro` Always Free VM, Oracle Cloud's Always Free Ampere A1 ARM VM, a rewrite of the bot's transport onto Discord's HTTP Interactions Endpoint model deployed on Google Cloud Run, and the same rewrite deployed on Cloudflare Workers - weighed against this project's actual conventions (`AGENTS.md`), its CD posture ([ADR 0011](0011-deploy-target-cloud-run-neon.md)'s Workload Identity Federation, no long-lived cloud credential ever stored as a GitHub secret), Discord-bot best practice, and pragmatism, including how well each option's *pattern* (not just this one bot) would extend to future `apps/*` additions.

**Both bare-VM options were rejected on the same structural grounds ADR 0011 already used to reject Oracle for `apps/api` itself** - "bare infrastructure, not a platform... no Dockerfile-native deploy, self-managed via SSH." That objection is about CD/ops maturity, not about the specific workload's shape, so it applies here just as much as it did to a stateless HTTP API: a hand-rolled SSH deploy, or a self-hosted GitHub Actions runner co-located with the box it deploys to, is a materially bigger attack surface than WIF's short-lived, narrowly-scoped tokens - and on a public repo, a self-hosted runner is a documented risk vector for fork-PR-triggered code execution. Oracle compounds this with a third cloud-provider account, an inconsistently-granted free-tier signup/capacity process, and a "permanent" allowance that was already cut once (halved from 4 OCPU/24GB to 2 OCPU/12GB on June 15, 2026) - undermining the "genuinely indefinite free tier" bar ADR 0011 set in the first place.

**Keeping the Gateway alive on Cloud Run itself doesn't work either.** A live Gateway WebSocket forces `min-instances: 1`, forfeiting Cloud Run's real scale-to-zero "Always Free" tier and costing real recurring money (a 1 vCPU/0.5GiB always-on instance was estimated around $11.61/month) - reopening exactly the "genuinely indefinite free tier, not a trial clock" question ADR 0011 already closed for this project.

**Checked directly against the code, not assumed: the bot does not structurally need the Gateway at all.** Every interaction it handles - slash commands, autocomplete, buttons, select menus, modals - is something Discord can deliver over a plain HTTPS webhook instead, via its documented, officially-supported "Interactions Endpoint URL" model (Discord itself publishes a reference implementation, `discord/cloudflare-sample-app`). Grepping every `interaction.*` call across `src/commands/*.ts` and `src/commands/index.ts` shows the actual surface any command touches is narrow: `deferReply`/`editReply`/`reply`/`followUp`/`deferUpdate`/`update`/`showModal`/`respond`, `options.getString`/`getInteger`/`getFocused`, `user.id`, `customId`, `values`, `fields.getTextInputValue`, `channelId`/`guildId`/`commandName`, the `deferred`/`replied`/`responded` flags, `isFromMessage()`, and the five `isX()` type guards (`isChatInputCommand`/`isAutocomplete`/`isStringSelectMenu`/`isButton`/`isModalSubmit`) - nothing touches `interaction.member`, permissions, or anything else discord.js's gateway-delivered objects carry that a webhook payload wouldn't. Better still: every existing test already exercises commands against a plain duck-typed object satisfying exactly that surface, not a real discord.js class instance (e.g. `tests/unlink-command.test.ts`'s `fakeInteraction()`, `tests/drop-command.test.ts`'s `fakeButton`/`fakeModalSubmit`/`fakeSelectMenu`, all built as `{...} as unknown as XInteraction & {...}`). This means the migration's real blast radius is the *transport layer* - `src/index.ts`, a new `/interactions` route, `src/commands/types.ts`'s interaction types - not a rewrite of every command's business logic.

**Cloudflare Workers (the same rewrite, a different host) was a legitimate, close second, not a bad option.** It's arguably the more idiomatic pattern - Discord's own sample app targets it directly - and its cold-start margin against Discord's 3-second interaction-ack window is better than a Cloud Run container's. It loses here on two grounds specific to this project: it forces a *second*, independent migration, since Workers' runtime has no raw TCP sockets and the existing Drizzle/`node-postgres` connection to the shared `loot_bot` Postgres schema would need Cloudflare Hyperdrive or Neon's HTTP-fetch driver instead; and it reintroduces a long-lived static API token sitting in GitHub Secrets, since Cloudflare has no WIF-equivalent OIDC federation yet - a real, if smaller-blast-radius-than-a-VM, regression from the exact property WIF was adopted to guarantee. Worth revisiting if either changes.

## Decision

Rewrite `apps/loot-bot`'s interaction transport from the Discord Gateway to Discord's HTTP Interactions Endpoint model, and deploy it on Google Cloud Run, reusing `apps/api`'s existing CD pipeline (same GCP project, same Workload Identity Federation, same Artifact Registry pattern, same `google-github-actions/deploy-cloudrun` action) nearly verbatim.

Concretely:

- `src/index.ts` drops the discord.js `Client`/`GatewayIntentBits`/`.login()` entirely. The process becomes a plain HTTP service - config, http server, listen - matching `apps/api`'s own request/response shape.
- A new `/interactions` route on the existing bare `node:http` server (alongside `/healthz` and `/auth/callback`) verifies each request's Ed25519 signature via Discord's own `discord-interactions` npm package (`verifyKey`, against the `X-Signature-Ed25519`/`X-Signature-Timestamp` headers and the *raw* request body), answers Discord's own endpoint-verification `PING` (interaction type 1) with `{type: 1}`, and otherwise builds a small adapter object satisfying the same narrow interaction interface every command already expects, then dispatches through the existing `commands/index.ts` logic (guildId check, customId-prefix routing, per-command `execute`/`onSelectMenu`/`onButton`/`onModalSubmit`) unchanged.
- Initial acknowledgment (`reply`, or a deferred type-5 response) happens by returning a JSON body directly from the `/interactions` handler within Discord's 3-second window. `editReply`/`followUp`/`update`/`deferUpdate` become `fetch` calls against that interaction's own webhook (`.../webhooks/{application_id}/{interaction_token}/...`), valid for its 15-minute follow-up window.
- Anything that outlives that window - notably `/drop`'s later message refresh and apply-claims summary, since a loot-drop session can span a real GM session - already uses a normal bot-token-authenticated Discord REST call today, not the Gateway; this was never Gateway-dependent and needs no change.
- discord.js's builder classes (`SlashCommandBuilder`, `EmbedBuilder`, `ButtonBuilder`, `StringSelectMenuBuilder`, `ModalBuilder`, `TextInputBuilder`, `ActionRowBuilder`) are pure JSON constructors with no Gateway dependency and are kept exactly as they are throughout `format-*.ts` and every command's `definition`.
- `src/db.ts` (Drizzle over `pg`, real TCP to the shared Postgres/Neon instance) is unchanged - this is the concrete advantage over the Cloudflare Workers alternative.
- New required config: `DISCORD_PUBLIC_KEY` (from the Discord Developer Portal's own "General Information" page), used for signature verification. `DISCORD_BOT_TOKEN` is retained - still needed for bot-token-authenticated REST calls (message edits, command registration).
- New `.github/workflows/deploy-loot-bot.yml`, mirroring `deploy-api.yml`: path-filtered on `apps/loot-bot/**`, run tests, auth via the same Workload Identity Federation provider/service account already used for `apps/api`, build/push to a new Artifact Registry repo, run `db:migrate` against the shared Neon instance's `loot_bot` schema, deploy via `google-github-actions/deploy-cloudrun`, curl the new revision's `/healthz`.
- One manual, one-time Developer Portal step (documented in `apps/loot-bot/README.md`'s Setup section, alongside its existing manual Discord/Authgear steps, and in `docs/operations/deployment-setup.md`): set the application's "Interactions Endpoint URL" to the deployed Cloud Run URL's `/interactions` path.

## Consequences

- A real, indefinite, $0 deploy path, on infrastructure this project has already audited and trusts - and a second app extending the exact "one GCP project, one WIF-based CD template" pattern `AGENTS.md`'s own mise-task convention already established for CI, now extended to deployment: a template for a third or fourth `apps/*` addition, rather than a fresh decision each time.
- The bot's interaction layer no longer has a live Gateway connection, so any future feature genuinely requiring Gateway-only data (message content, presence, voice, guild member events) would need its own separate answer. Not expected to be needed given this bot's scope ([ADR 0050](0050-loot-bot-stack-linking-and-isolation.md)/[0051](0051-loot-bot-give-command.md)/[0052](0052-loot-bot-loot-drop-and-claims.md)), but a real, if currently costless, constraint being accepted here.
- Gave up Cloudflare Workers' arguably-more-idiomatic "official Discord sample app" pattern and its lower cold-start latency against the 3-second ack window, in exchange for keeping WIF's no-stored-credential CD property and avoiding a second, independent Postgres-driver migration. Revisit if Cloudflare ships a WIF-equivalent OIDC federation, or if Cloud Run cold starts prove to be a real problem in practice.
- Real, one-time migration cost: `src/index.ts`, a new `/interactions` route and interaction adapter, and `src/commands/types.ts`'s interaction type imports change. Individual command files are expected to need little to no change beyond that, since every existing test already exercises them against a plain object satisfying the same narrow interface the new adapter provides - confirmed directly against the current test suite, not assumed - but this is verified command-by-command during implementation, not just inferred from the test shape.
- Deferred, not decided here: whether to keep the full `discord.js` package (used only for its builder classes going forward) or slim down to the standalone `@discordjs/builders` package - a small dependency-hygiene call, not an architectural one.

## Addendum: `/healthz` renamed to `/livez` - Google Front End reserves the exact path `/healthz` on every `*.run.app` host

The real, deployed service returned Google's own generic 404 page for `/healthz` - not this app's own plain-text 404, and with zero Cloud Run request-log entries for it, meaning the request never even reached the container. `apps/api`'s own `/healthz` (a genuinely registered FastAPI route) shows the identical symptom on its own deployed service; its deploy pipeline never caught this only because its own smoke test curls `/readyz`, never `/healthz`. Confirmed as a known, documented Cloud Run/GFE behavior (not a bug in either app): GFE intercepts the literal path `/healthz` before it reaches any container, on any `*.run.app` host, while sibling paths (`/livez`, `/readyz`, `/health`) pass through untouched.

Renamed this bot's liveness route from `/healthz` to `/livez` (`src/http-server.ts`'s `livezRoute`, `src/index.ts`'s route map, `deploy-loot-bot.yml`'s own smoke-test curl) - the same name Kubernetes' own modern liveness-probe convention uses, for the same underlying reason Kubernetes moved past plain `/healthz` too. `apps/api`'s equivalent route was left alone: it's a real, if now known to be internet-unreachable-by-that-exact-name, endpoint, and changing a different app's API surface wasn't in scope here.
