# 0036 - User, player, and character CRUD API

Status: accepted

## Context

`app_user`/`membership`/`player`/`being`/`character` ([ADR 0031](0031-character-table-and-read-api.md)) have had a read-only REST surface, but no mutation path at all - [ADR 0010](0010-user-tenant-membership-model.md) named "how a GM adds a player to their tenant" as a real open question, still true until now. This ADR accepts [RFC 0007](../rfcs/0007-user-player-character-crud-api.md), close to verbatim - see it for the full reasoning trail. It is the largest slice of this milestone: user deletion, membership invite/role-change/revoke, player join/leave, and character create/promote/update/demote/roster-links, each with its own authorization tier.

`campaign_access.can_manage_campaign`/`can_manage_any_campaign_in_tenant`/`campaign_ids_for_character`/`can_manage_any_of_campaigns` and `entity_access.controlled_character_entity_ids`/`can_self_manage_entity` already exist ([ADR 0032](0032-item-and-item-instance-crud-api.md)/[ADR 0034](0034-campaign-crud-api.md)). This ADR *consumes* every one of those as-is; it adds exactly two new predicates to `campaign_access.py` - `can_manage_every_campaign` and `campaign_ids_for_players` - detailed below.

## Decision

### User: `DELETE /me` only

`app_user` has no editable field ([ADR 0009](0009-identity-provider-authgear.md)'s boundary - no name/email/avatar lives here), so there's no `PATCH /me`. `DELETE /me` removes the caller's own row; every `Membership`/`Player`/`CampaignGm`/`TenantAdminCampaignOptOut` row they held, in every tenant, is cascade-deleted, and every `created_by`/`updated_by` they ever left behind (`entity`, `campaign`, `membership`, `player`, `character`, `campaign_gm.created_by`, `tenant_admin_campaign_opt_out.created_by`) is `SET NULL` - both already the FK behavior [ADR 0029](0029-attribution-created-by-updated-by.md) established, triggered here for the first time by a real delete rather than assumed. **Guarded: `409 LastOwnerError` if the caller is the sole `OWNER` `Membership` of any tenant** - checked for every tenant they own *before* anything is deleted, so one failing tenant can't leave a half-completed deletion behind. Confirmed empirically, not just reasoned through, that Postgres's referential-integrity actions (the cascades/`SET NULL`s above) bypass row security regardless of `app.tenant_id` - membership's own RLS policy only needs to be set (per tenant, in the guard's own pre-check loop) for the *count* query that decides whether the guard fires at all.

### Membership: invite, change role, revoke - `OWNER`-only

`POST`/`PATCH`/`DELETE /tenants/{id}/memberships[/{user_id}]`, all gated by `get_tenant_context` **and** `OWNER` specifically, not `ORGA` (`403 MembershipManagementForbiddenError` otherwise) - a deliberate narrowing: granting/revoking tenant-wide administrative access is more sensitive than day-to-day tenant administration. `POST` takes `{user_id, role}` (`user_id` must already be a real `app_user` row - this API has no email to invite by, [ADR 0009](0009-identity-provider-authgear.md)'s boundary; `422 InvalidUserError` otherwise, `409 MembershipAlreadyExistsError` if already a member - neither named in the RFC's own text, both added so a real, easily-reachable case gets a clean typed response instead of an unhandled composite-PK-violation 500). `PATCH` takes `{role}`. `DELETE` additionally allows removing your own membership (leaving the tenant) without `OWNER`, mirroring `revoke_campaign_gm`'s self-removal carve-out. **`PATCH`/`DELETE` both guard the last-`OWNER` case** (`409 LastOwnerError`), the same structural concern `DELETE /me` guards from the other direction. `created_by`/`updated_by` land on `membership` in this same migration (the last table named in [ADR 0029](0029-attribution-created-by-updated-by.md)'s phased table); `POST` sets both to the inviting owner, `PATCH` updates `updated_by` to whichever owner changed the role. `POST` has no `Location` header, deliberately: unlike every other `POST` in this codebase, there is no single-resource `GET .../memberships/{user_id}` route to point one at (only the broadened roster list, [ADR 0031](0031-character-table-and-read-api.md)), and this ADR doesn't invent one just to have somewhere to point.

### Player: join and leave

`POST`/`DELETE /tenants/{id}/campaigns/{id}/players[/{player_id}]`, gated by `get_campaign_context` + `can_manage_campaign` for adding (a GM building their own roster, or a tenant admin - not self-service, since no invite-link/visibility mechanism exists yet that would make "join any campaign you can see" safe); removal additionally allows the player leaving voluntarily. No `PATCH` - a `Player` row has nothing mutable beyond the FKs that define its identity. `created_by`/`updated_by` land on `player` in the same migration as `membership` above (both, per [ADR 0029](0029-attribution-created-by-updated-by.md)'s phased table, land with this ADR); both always equal the managing GM/admin, since self-service joining doesn't exist yet.

### Character: create, promote, update, demote, roster links

`POST /characters` (self-or-managed, `CharacterCreate{name, owner_player_id, player_ids}` -> `201`), `PUT /characters/{id}` (`CharacterPromote{owner_player_id}` -> `201` first call / `200` on a repeat), `PATCH /characters/{id}` (`CharacterUpdate{name, owner_player_id}` -> `200`), `DELETE /characters/{id}` (-> `204`), `PUT`/`DELETE /characters/{id}/players/{player_id}` (-> `200`). The router's own gating dependency moves from `get_tenant_context` to `get_tenant_or_404` (mirroring [ADR 0032](0032-item-and-item-instance-crud-api.md)'s identical `item_instances.py` precedent) - a plain player rolling their own PC has no tenant-wide `Membership` row, so gating the whole router on one would lock self-service out entirely. The two pre-existing `GET` routes ([ADR 0031](0031-character-table-and-read-api.md)) each re-add their own explicit tenant-membership check instead (`_require_tenant_member`), preserving their original "only tenant-wide members reach this" behavior unchanged - a deliberate, minimal-blast-radius fix the RFC's own text doesn't spell out but that changing the router-level dependency requires.

`POST` always creates `Entity` + `Being` + `Character` + one `CharacterPlayer` per touched player id, in one transaction, folding `owner_player_id` into the roster automatically if given and not already present. `PUT` promotes an existing `being`; idempotent, `201`/`200` as above; the first call sets `character.created_by`/`updated_by` to the promoter while `entity.created_by` keeps whatever it already was (this is exactly the case [ADR 0029](0029-attribution-created-by-updated-by.md)'s `character`/`entity` split exists for), a repeat call touches only `character.updated_by`. `PATCH` renames (touches `entity.name`/`updated_by` - `name` is `entity.name`, not a `Character` column) and/or reassigns `owner_player_id` (touches `character.owner_player_id`/`updated_by`, folding the new owner into the roster too); which happened decides the authorization tier below. `DELETE` demotes - deletes only the `character` row; `CharacterPlayer`/`GroupMember` rows referencing it cascade away with it, but `being`/`entity` and anything the character owned, contained, or knew (`Ownership`/`Containment`/`Knowledge`, all plain `FK -> entity.id`, [ADR 0025](0025-character-being-and-ownership.md)/[ADR 0028](0028-knowledge-and-group-membership.md)) survive untouched - no data-integrity guard needed, since demotion is inherently non-destructive to anything but the character-specific links.

**The three-way "managed" authorization split**, each its own function in `routers/characters.py`, consuming its own `campaign_access.py` predicate:

- **Roster-link tier** (`_authorize_roster_touch`) - `POST`'s `player_ids`/`owner_player_id`, `PUT`/`PATCH`'s `owner_player_id` when it's actually changing, and the roster sub-resource `PUT`/`DELETE`'s own `{player_id}`. Self-service if every touched player id is one the caller holds (validated to exist first - `404 PlayerNotFoundError` on a bogus id). Managed: **`can_manage_every_campaign`** (new) over every campaign among the touched ids' own campaigns (`campaign_ids_for_players`, new) - "no more and no less," standing needed everywhere the write actually acts, not just anywhere it happens to also touch. Falls back to `can_manage_any_campaign_in_tenant` when there's nothing to scope to at all (an ownerless NPC, or clearing `owner_player_id`).
- **Any-one-current-campaign tier** (`_authorize_rename`) - a `PATCH` that touches only `name`. Self-service reuses `controlled_character_entity_ids` directly (the character references no player id of its own for a plain rename to check against). Managed: `can_manage_any_of_campaigns` over `campaign_ids_for_character`'s current roster - RFC 0005's identical "already uniformly visible everywhere it's rostered, one GM's oversight is enough" reasoning. Same tenant-wide fallback for a character rostered nowhere at all.
- **Every-campaign tier** (`_authorize_demote`) - `DELETE`. Same `controlled_character_entity_ids` self-check as rename. Managed: **`can_manage_every_campaign`** over the character's *entire* current roster (`campaign_ids_for_character`) - demotion ends its presence everywhere at once, so every campaign needs to consent, not just one. Same tenant-wide fallback for a character rostered nowhere (without it, a totally unrostered character's demotion would be authorized by a vacuous `all([])` regardless of who's asking - not something the RFC's own text names, but a real gap its "every campaign it belongs to" wording leaves open when that set is empty; closed here the same way the roster-link tier's own "nothing to scope to" case already is).

`If-Match`/`check_if_match` is reused verbatim across every character write route, checked against `entity.updated_at` specifically - `character` itself has no `created_at`/`updated_at` columns of its own ([ADR 0031](0031-character-table-and-read-api.md) never added them), so the underlying `Entity`'s timestamp is the natural ETag surrogate for the whole `being`-plus-`character` aggregate, the same row `GET /characters/{id}` already reaches through to build `name` from.

### New `campaign_access.py` predicates

- **`can_manage_every_campaign(session, *, user_id, campaign_ids, tenant_id)`** - `can_manage_campaign` on *every* one of `campaign_ids`, the "all, not any" counterpart to the existing `can_manage_any_of_campaigns`. Consumed by both the roster-link tier (over the touched set) and the every-campaign tier (over a character's full current roster) - genuinely the same predicate at two different scales, not two different rules.
- **`campaign_ids_for_players(session, *, player_ids, tenant_id)`** - every campaign a given set of `Player` rows belongs to, resolved directly (unlike `campaign_ids_for_character`'s `CharacterPlayer` walk, which needs an already-existing character to start from - `POST`/`PUT` don't have one yet at authorization time).

### Schemas

`schemas/characters.py` gains `CharacterCreate`/`CharacterPromote`/`CharacterUpdate`. `schemas/players.py` gains `PlayerCreate{user_id}` and adds `created_by`/`updated_by` to `PlayerOut` (per that module's own forward-looking comment). `schemas/tenants.py` gains `MembershipCreate{user_id, role}`/`MembershipUpdate{role}` and adds `created_by`/`updated_by` to `MembershipRosterEntryOut`/`PlayerRosterEntryOut` (ditto).

## Not in scope

Campaign/GM-grant mutation ([ADR 0034](0034-campaign-crud-api.md)). Character "retirement" as a soft-delete alternative to demotion. Per-player character caps. Fully destroying a `being`/`entity`, or creating a bare `being` with no `character` row - both remain generic being/entity-lifecycle concerns with no CRUD path anywhere in this codebase yet.

## Consequences

- One migration: `membership`/`player` gain the full `created_by`/`updated_by` pair (nullable, `ON DELETE SET NULL`, indexed) - the last two rows in [ADR 0029](0029-attribution-created-by-updated-by.md)'s phased table. Both tables' `User`-side relationships (and `User.memberships`/`User.players`) needed explicit `foreign_keys=` disambiguation as a result, the same fix `campaign_gm`/`tenant_admin_campaign_opt_out` already needed in [ADR 0034](0034-campaign-crud-api.md).
- `can_manage_every_campaign`/`campaign_ids_for_players` join `campaign_access.py`; `LastOwnerError`, `MembershipManagementForbiddenError`, `MembershipNotFoundError`, `MembershipAlreadyExistsError`, `PlayerAlreadyExistsError`, `InvalidUserError`, and `CharacterManagementForbiddenError` join `exceptions.py`.
- `routers/characters.py`'s gating dependency changes from `get_tenant_context` to `get_tenant_or_404`, with the two pre-existing `GET` routes re-adding their own explicit membership check - a real behavior-preserving fix this RFC's own text doesn't call out, required by self-service reaching the router at all.
- `DELETE /me`'s last-owner guard, `DELETE /characters/{id}`'s survive-the-cascade behavior, and `PUT /characters/{id}`'s two-status-code branches each have their own explicit test, per the RFC's own "Consequences" callouts - none of the three is covered incidentally by a shared happy-path test.
- The three-way "managed" split has its own test matrix (roster-link including its ownerless fallback, any-one-current-campaign, every-campaign including its own unrostered-character fallback) - three separate predicates over three separate campaign sets, not one shared helper.
