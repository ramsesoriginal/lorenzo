# 0039 - A generic `v_effective_stat` view, read by everything that shows stats

Status: accepted

## Context

[ADR 0037](0037-effective-stat-resolution.md) built prototype-graph stat resolution but scoped it narrowly, and flagged the narrowing explicitly in its own "Not resolved by this change" section. Reviewing that ADR surfaced two consequences of the scoping worth re-examining, both raised in conversation rather than by a new incident or milestone requirement:

- The recursive CTE (`stat_ancestor`/`ancestor_priority`/`resolved_stat`) is inlined once each inside `v_item`'s and `v_item_instance`'s own `CREATE VIEW` SQL, and only ever resolves the 8 stat names those views hardcode as columns (`weight, height, price, rarity, hp, armor, is_magical, is_cursed`). Any other stat a tenant defines - a custom `strength`, `mana`, whatever a game system needs - is invisible through `v_item`/`v_item_instance` regardless of resolution, because the view was never plumbed to expose it as a column at all. This isn't new to ADR 0037; the pre-resolution view had the identical 8-name limit.
- `EntityViewMixin.physical_stats`/`economic_stats`/`destroyable_stats`/`damaging_stats`/`tags` (`models/entity_view_mixin.py`), and `EntityDetailOut.stats` (`GET /entities/{id}`'s own stats field, `schemas/entities.py`), walk `Entity.stats` directly - an entity's own `entity_stat` rows only, no inheritance at all, for any stat, including the 8 that resolve correctly through `ItemOut.weight`/etc. An item that inherits "weight" through a prototype chain shows the correct resolved value in `ItemOut.weight` and a stale-or-missing one in that same response's `physical_stats` list.

A third fact, true independent of scope but relevant to the fix: `entity_prototype` was always entity-generic, not item-specific ([RFC 0001](../rfcs/0001-core-domain-data-model.md)/[ADR 0015](0015-entity-prototype.md) - any entity can prototype any entity), and `VCharacter` already reuses the identical `EntityViewMixin` ([ADR 0031](0031-character-table-and-read-api.md)). A character stood to inherit stats through a prototype exactly the way an item does, but never could - the resolution CTE's base case only ever started from `item`/`item_instance` rows.

This ADR resolves both gaps directly, as a follow-up to an already-accepted design rather than a new open question - mechanically an extension of ADR 0037's own resolution rule, not a reconsideration of it, so it isn't routed through a fresh RFC first.

## Decision

### A new, generic `v_effective_stat` view owns the walk

`v_effective_stat(entity_id, tenant_id, stat_definition_id, value_int, value_text, value_float, value_bool)` - one row per (entity, stat_definition) pair that resolves to something, for every `stat_definition`, for every entity in the tenant, not just item/item_instance-typed ones and not just the 8 names `v_item`/`v_item_instance` happen to expose. Holds the same three CTEs ADR 0037 already decided (`stat_ancestor`, `ancestor_priority`, the `DISTINCT ON`-based final `SELECT`), unchanged in logic, with one change to `stat_ancestor`'s base case: `FROM entity e` (every entity), not `JOIN item st ON st.entity_id = e.id` / `JOIN item_instance st ON st.entity_id = e.id`. The resolution rule itself - hop-0 always wins, then hop distance, then the acquired-stat-group priority tie-break, then `ancestor_id` - is unchanged; this ADR relocates and generalizes where the walk runs, it doesn't revisit what it decides.

`security_invoker = true`, same reasoning as `v_item`/`v_item_instance`: every table the CTEs touch (`entity`, `entity_prototype`, `entity_stat`, `entity_stat_group`, `stat_group`) already carries its own tenant-scoped RLS policy, so the walk stays correctly scoped without an explicit filter of its own.

### `v_item`/`v_item_instance` become consumers of the walk, not owners of it

Each of their 8 named-stat `LEFT JOIN` subqueries changes its `FROM` clause from the inline `resolved_stat` CTE to `v_effective_stat` - otherwise unchanged: still one `LEFT JOIN (SELECT ... FROM v_effective_stat ves JOIN stat_definition sd ON sd.id = ves.stat_definition_id WHERE sd.name = '<stat>') <stat> ON <stat>.entity_id = e.id` per name, still 8 separate joins, still the same plain-column output shape as today. Deliberately *not* rewritten into a single join-plus-pivot (e.g. `MAX(...) FILTER (WHERE sd.name = ...)`) - that would also work and touch fewer lines, but introduces a `GROUP BY` where none exists today for a benefit (fewer joins) this change doesn't need. Keeping the per-name-subquery shape means the diff is exactly "swap the CTE's source," nothing else about either view's structure moves. The `WITH RECURSIVE ...` block itself is deleted from both views' `CREATE VIEW` SQL - it now lives solely in `v_effective_stat`.

### `EntityViewMixin` and `GET /entities/{id}`'s `stats` field read through it too

`Entity` gains a new `effective_stats` relationship - `viewonly=True`, mapped over `v_effective_stat` the same way `VItem.entity`/`VItemInstance.entity` are mapped over `entity` today (an explicit `primaryjoin`, since a view has no real `ForeignKey` to infer one from). `_stats_for_group`/`tags` (`models/entity_view_mixin.py`) switch from iterating `self.entity.stats` to `self.entity.effective_stats`, filtering on `stat_definition.stat_group.name` exactly as before. `EntityDetailOut.stats` (`schemas/entities.py`) switches its `StatValueOut.from_entity_stat(stat) for stat in entity.stats` to iterate `entity.effective_stats` the same way; `from_entity_stat` needs no logic change, since it already only touches `stat.stat_definition`/`value_int`/`value_text`/`value_float`/`value_bool` - the same shape both `EntityStat` and the new `VEffectiveStat` model expose (its parameter type widens accordingly, from `EntityStat` specifically to whatever narrow structural type covers both, rather than gaining a second near-identical classmethod).

`Entity.stats` (the direct, non-inherited relationship, backed by the real `entity_stat` table) is unchanged and stays exactly as it is today - `routers/entity_stats.py`'s `PUT .../stats/{id}` writes it via `session.get(EntityStat, ...)` directly, not by navigating `entity.stats`, so it needs no eager-loaded relationship at all.

Every eager-load chain that currently loads `Entity.stats` purely for display (`routers/entities.py`'s `get_entity_detail_or_404`, `routers/items.py`'s `eager_load_options`, reused by `routers/item_instances.py`) replaces that with `selectinload(Entity.effective_stats).selectinload(VEffectiveStat.stat_definition)` - confirmed, not assumed, that nothing else in either chain's call sites still needed `Entity.stats` loaded once the response schemas above moved to `effective_stats`.

## Not in scope

Everything ADR 0037 already excluded and this doesn't reopen: caching/materializing effective stats, multi-game-system stat scoping, `stat_group`/`stat_definition` list/update/delete. Not changing the priority tie-break rule, the depth bound, or any authorization check - this is a read-path deduplication and generalization over an already-decided resolution mechanism, not a new mechanism. Not adding a 9th+ named column to `v_item`/`v_item_instance` for tenant-defined stats beyond the existing 8 - `GET /entities/{id}`'s `stats` field (via `effective_stats`) is how those become visible, not the item-shaped named fields.

## Consequences

- One new migration (`4768ec40991a`): creates `v_effective_stat`, then drops and recreates `v_item`/`v_item_instance` against it (create the new view first, then replace the two dependent views, mirroring the dependency order [ADR 0037](0037-effective-stat-resolution.md)'s own migration already established for `v_item_instance` before `v_item`). `downgrade()` reverses that: drop `v_item`/`v_item_instance` (the dependents), then `v_effective_stat`, then restore [ADR 0037](0037-effective-stat-resolution.md)'s own inline-CTE `CREATE VIEW` SQL verbatim (inlined here rather than imported from `6341fedbfc47`, matching that migration's own precedent of inlining its predecessor's SQL for the same reason: a self-contained snapshot downgrade can always replay).
- `ItemOut`/`ItemInstanceOut`'s `physical_stats`/`economic_stats`/`destroyable_stats`/`damaging_stats`/`tags`, and `GET /entities/{id}`'s `stats` field, now agree with `weight`/`hp`/`armor`/etc. on the same underlying data - the known, accepted inconsistency [ADR 0037](0037-effective-stat-resolution.md) flagged is closed, not just re-documented.
- Characters (and any other entity with a prototype link, not only items/item-instances) now resolve inherited stats too, through the same `v_effective_stat` view `VCharacter`'s own `EntityViewMixin` properties already read from - a real capability extension beyond what any milestone has asked for, but a direct, low-risk consequence of making the walk entity-generic rather than item-typed-table-generic, not something separately designed here.
- `v_item`/`v_item_instance` lose their only `WITH RECURSIVE` block; `v_effective_stat` is now the one place the prototype-stat walk exists, so any future change to the resolution rule (the tie-break, the depth bound) touches one view instead of two.
- A tenant-defined stat outside the 8 names `v_item`/`v_item_instance` hardcode now resolves with inheritance and is visible via `GET /entities/{id}`'s `stats` field - it still won't appear as a named field on `ItemOut`/`ItemInstanceOut` (`weight`, `hp`, ...), since those 8 names were never meant to be exhaustive of every possible stat, only the specific ones ADR 0019 chose to surface as plain columns.
