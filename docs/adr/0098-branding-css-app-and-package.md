# 0098 - Branding CSS: apps/brand + packages/brand, same-origin default

Status: accepted

## Context

[Discussion #133](https://github.com/ramsesoriginal/lorenzo/discussions/133)'s third proposal named a real, confirmed problem: `apps/inventory-web` and `apps/account-hub` already carry a byte-identical, independently-copied `tokens.css`/`base.css`, and a third frontend is a named possibility (ADR 0007). `docs/brand/identity.md` §6.6 is now the authored source of truth for the actual semantic color/spacing/radius/shadow values (see the `feat/branding-refinement` work, merged in PR #176) — this ADR is about how those values actually reach running apps instead of being hand-copied into each one.

The discussion also named the real tradeoff up front: a build-time npm dependency is safe and independent but needs every consumer redeployed to see a change; a runtime-hotlinked stylesheet propagates instantly but creates a live uptime coupling between every frontend and wherever it's served from. This project is AGPL-3.0 — self-hosting is a first-class use case (README, LICENSE) — so a design that only works by pointing every deployment at one centrally-run host is a real regression for anyone who forks and runs their own copy.

Prior art for exactly this shape of problem: [stoatchat/for-web#1356](https://github.com/stoatchat/for-web/issues/1356) hit a hardcoded-CDN-breaks-self-hosting bug and fixed it with a `VITE_STATIC_URL` build-time env var defaulting to the official host, overridable to a self-hoster's own mirror. BentoPDF (also AGPL) uses the same family of build-time URL-override flags.

## Decision

Two new things, one hand-edited source:

- **`apps/brand`** — a plain static site, no framework and no build step: a small **layout package**, not just tokens, so that including any one file gets you opinionated, on-brand defaults rather than a bare palette. Seven files, in the order any consumer should load them: `normalize.css` (a minimal modern reset, ported verbatim from `apps/inventory-web` — it has zero token references, so it's identical), `tokens.css` (colors/font-names/spacing/radius, identity.md §6/§5.2/§8.1/§8.3), `fonts.css` + `fonts/*.woff2` (the actual self-hosted `@font-face` files backing those font-family names — vendored from the exact `@fontsource-variable/{geist,geist-mono,newsreader}` packages `inventory-web`/`account-hub` already use, not a Google Fonts/CDN link, matching identity.md §17.2's "self-host all assets" rule applied to fonts too), `base.css` (sensible bare-element defaults, plus `scrollbar-gutter: stable` globally), `layout.css` (the generic subset of `inventory-web`'s own file — page shell, brand lockup, section-spacing rhythm, and a `.with-sidebar`/`.sidebar` two-column page shell alongside the original single-column `.wrap`; domain-specific layout like a kanban board's columns stays local to the app that needs it), `components.css` (buttons, form controls including `textarea`/`select`/checkbox/radio/range/a custom `.switch` toggle, tabs, chips, badges, status pills, the neutral visibility-badge treatment, native `dialog`/`dialog::backdrop` styling, a `.tree` nested-disclosure pattern built on `<details>`/`<summary>`, and `.editor-toolbar`/`.editor-content` for a custom rich-text-style editor — a curated generic subset of `inventory-web`'s and `account-hub`'s own `components.css` plus genuinely new patterns neither app had yet, not a full port: item cards, board columns, and catalog rows stay app-local), and `motion.css` (every animation pattern the brand actually uses, identity.md §11: routine `.spinner`/`.skeleton`/`.progress-bar`, the rare branded `.spark-loader`, `.glow-canonical` as a literal conic-gradient halo for Gold's one job, and opt-in editorial effects — `.typewriter`, `.stat-count` count-up, `.reading-progress` scroll-linked bar, `.stagger` sibling fade-in, `.squircle` corners — with every experimental technique, `corner-shape`, `sibling-index()`, `animation-timeline: scroll()`, wrapped in `@supports` with a plain static fallback, and a global `prefers-reduced-motion: reduce` override on top of everything else). Plus `preview/*.html` pages that `<link>` to all seven in order via relative paths, so they open and render correctly straight off disk via `file://` with no server running, the same way `docs/brand/assets/showcase/index.html` already does — six further preview pages beyond the original tokens/components tour exercise motion, dialogs (including two non-modal, semi-overlapping ones open at once), forms, trees, a custom editor, and `preview/content/`'s seven "thematic lorem ipsum" pages (a 1993 tax office, a university research project, a starship crew, a Renaissance merchant family, a cyberpunk corporation, a mundane apartment inventory, a traditional fantasy campaign) proving the style reads well across content that has nothing to do with Lorenzo's own domain. Deployed to Cloudflare Pages via Git integration (no GitHub Actions workflow needed — same exception already used for `inventory-web`/`account-hub`, see [docs/guides/adding-an-app.md](../guides/adding-an-app.md)).
- **`packages/brand`** — a thin npm package (`@lorenzo/brand`) whose only job is making that same set of files `pnpm add`-able by other apps in the workspace for build-time bundling. Its `mise.toml` `build` task copies each file (plus the whole `fonts/` directory) from `apps/brand` into itself; those copies are `.gitignore`d (never hand-edited, never committed) and removable on demand via a separate `mise run //packages/brand:clean` task. Consuming apps that need the files present just need `packages/brand:build` to have run first (a `depends` relationship, same mechanism `install` already is for `lint`/`test`/`build` in the existing app `mise.toml`s) — deleting them automatically on every build was considered and rejected: the files have to still exist when a *consumer's* build reads them through the pnpm workspace symlink, so "delete right after copying" would delete them before anything downstream ever saw them.

Consuming apps read a `PUBLIC_BRANDING_CSS_URL` config value (Astro's `PUBLIC_`-prefixed env var convention, so it's available client-side) that defaults to a same-origin path, `/branding/tokens.css` — that app's own build copies its `packages/brand`-sourced files to `public/branding/` so the default requires zero new runtime dependency and works out of the box for any self-hoster. Setting the var to an absolute URL (e.g. `apps/brand`'s own deployed Cloudflare Pages URL) opts a given deployment into the runtime-hotlinked, instant-propagation behavior across every app pointed at it — this project's own reference deployment is expected to do exactly that once this lands, but nothing forces it.

**`icons.svg` + `icons.manifest.yaml`** (identity.md §17's Tabler-based sprite system) round out the package — 40 hand-assembled `<symbol>`s covering every real icon-worthy action audited across `inventory-web`/`account-hub` (every button/link/aria-label in both apps' `src`, cross-referenced against identity.md §17.3/§18.2's own starter lists; tracked in [issue #178](https://github.com/ramsesoriginal/lorenzo/issues/178)), fetched directly from Tabler's own outline SVG source (MIT) and verified well-formed with no duplicate IDs. No build step here either, matching `apps/brand` everywhere else: adding an icon means fetching its real Tabler SVG and hand-adding one `<symbol>` block plus a manifest line, not running a generator. Several semantic names deliberately alias another entry's artwork (documented in the manifest) rather than mint a new `<symbol>` for a closely related action.

## Not in scope

- Actually wiring `PUBLIC_BRANDING_CSS_URL` into `inventory-web`/`account-hub` and dropping their own hand-copied `tokens.css` — a follow-up sub-slice once `apps/brand`/`packages/brand` exist and the content in them is proven.
- A DTCG-format token source + Style Dictionary build step. Deliberately deferred until a second, non-CSS consumer of the same token values actually exists (e.g. a future native mobile app) — building that pipeline now would be speculative given every current and named-future consumer is CSS.
- An immutable, version-pinned URL path (e.g. `/v/2026-09-23/tokens.css`) that could carry Subresource Integrity — real prior-art tension (SRI hash-pinning and "this URL updates instantly" are mutually exclusive on the same URL), deferred until a self-hoster actually asks for that guarantee.
- Publishing `packages/brand` to a public npm registry. It's consumed inside this monorepo via the pnpm workspace's own `workspace:*` protocol only, for now.
- The one-time Cloudflare Pages project setup itself (tracked the same way as the existing `inventory-web`/`account-hub` one-time setup, in `docs/operations/deployment-setup.md`, once there's something real to deploy).

## Consequences

- Editing the actual design tokens (or fonts, or layout, or a component) is editing a plain CSS file with no build step and an instant local preview — no framework, no dev server, no compile step between a change and seeing it.
- `apps/brand` and `packages/brand` both trace to the same hand-edited files, so there's exactly one copy of each to keep in sync with `identity.md`, not two.
- `packages/brand`'s working tree is only "clean" (no generated files present) right after an explicit `clean` run, or before the first `build` — this is a deliberate, documented manual step, not automatic, since automatic deletion on every build would need to run *after* every possible consumer's build too, which isn't something `packages/brand` itself can know about or trigger.
- Adds `packages/*` to `pnpm-workspace.yaml` for the first time (already anticipated there, per `docs/guides/adding-a-package.md`'s own comment placeholder).
- A self-hoster's default deployment gains zero new runtime dependencies; only a deployment that deliberately points multiple apps at one shared `apps/brand` host takes on the uptime coupling the original discussion flagged, and does so by explicit choice rather than by default.
- **Gotcha hit building `packages/brand`'s `build` task on Windows**: a multi-line `run` string only executed its first line, and a separate `mkdir -p` step failed outright ("The syntax of the command is incorrect") — `mkdir` is a `cmd.exe` builtin on Windows that shadows Git-for-Windows' real `mkdir.exe` and doesn't understand `-p`, unlike `cp`/`rm`, which aren't `cmd.exe` builtins and resolve to the real executables regardless. Fixed by using a `run` array of single-line steps and avoiding `mkdir` entirely (`rm -rf`+`cp -r` for the whole `fonts/` directory instead of `mkdir -p`+`cp *.woff2`) — worth remembering for any future cross-platform mise task that creates a directory.
- **Several real composition gotchas surfaced only once components were actually combined with each other on a real page**, not visible from any single component in isolation: `.card`'s own `overflow: hidden` (there to clip things like a swatch color to its rounded corners) silently clipped `.glow-canonical`'s halo to nothing when both classes landed on the same element, since the halo deliberately bleeds 2px past the border; `.tree summary .icon`'s disclosure-chevron rotation targeted *any* `.icon` in a summary, which also spun a second, semantic type icon placed next to the chevron; a bare `.card` used directly on an `<a>` (a whole card as the click target, first done in `preview/content/index.html`) inherited the base `a` rule's link-blue color into its own heading, since `.card` had never accounted for being a link; and `.with-sidebar`'s two-column grid needed an explicit `grid-column: 1 / -1` on a trailing `<footer>`, since grid auto-placement otherwise slots a third child into the narrow sidebar column alone. Each was only caught by actually composing the classes together on a real preview page and checking computed styles in a live browser, not by reading either rule on its own — worth remembering that this package's own test coverage is exactly that: real pages combining real components, not each stylesheet reviewed in isolation.
