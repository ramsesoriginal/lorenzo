# 0091 - inventory-web: a generated, typed API client

Status: accepted

## Context

`apps/inventory-web` talked to `apps/api` through a hand-rolled `apiFetch<T>(path, init)` (`lib/api.ts`): a bare `fetch()` wrapper where the path was a template string and the response type was whatever the caller asserted with `<T>`. Nothing checked that assertion against what the API actually returns - a renamed or removed response field, or a typo'd path, surfaced (if at all) as a runtime `undefined`/404 discovered by hand, not a build-time error. `lib/types.ts` hand-maintained its own copies of every response shape, kept in sync with `apps/api`'s real schemas by a code comment ("checked against its live openapi.json, not guessed") rather than anything the compiler enforced.

`apps/loot-bot` already solved this the same way `apps/inventory-web` needed to: `openapi-typescript` generates a schema types file from `apps/api`'s own OpenAPI schema, and `openapi-fetch` provides a client typed against it, so a path or response-shape mismatch is a compile error ([ADR 0050](0050-loot-bot-stack-linking-and-isolation.md); [ADR 0020](0020-rest-api-tenant-scoping-and-schemas.md) picked stable `operationId`s specifically to make that codegen viable). Nothing about `apps/inventory-web` argued for a different answer - this ADR adopts the identical pattern rather than inventing a second one, following [ADR 0004](0004-static-astro-frontend.md)'s own "island"/minimal-JS shape unchanged (the client is a plain module, not a framework).

This ADR is written after the implementation landed ([PR #140](https://github.com/ramsesoriginal/lorenzo/pull/140)), not before it - a process gap flagged directly by the user, not caught by the agent doing the work at the time. Recorded now for the same reason every other ADR exists: so the decision and its reasoning survive independently of that one PR's diff.

## Decision

### `lib/lorenzo-schema.d.ts` (generated, not hand-written)

Generated by `openapi-typescript` from `apps/api`'s own OpenAPI schema - `pnpm run generate-client` (`openapi-typescript ../api/openapi.json -o src/lib/lorenzo-schema.d.ts`), the identical `../api/openapi.json`-from-a-local-dump convention `apps/loot-bot`'s own `generate-client` script already established (`mise run //apps/api:openapi-schema` produces that local file; no network call, no live server - `app.openapi()` is pure introspection over already-registered routes, per that script's own docstring). Excluded from Biome's own checks (`biome.json`), matching `apps/loot-bot`'s identical exclusion - a generated file isn't hand-edited, so there's nothing for a formatter/linter to enforce on it.

### `lib/api.ts` - the typed client, a bearer-token middleware, and one shared error path

`createClient<paths>({ baseUrl })` (from `openapi-fetch`) replaces the old `fetch()` wrapper. A `Middleware` attaches the bearer token to every outgoing request (`onRequest`, throwing `ApiError(401, 'Not logged in.')` up front if none is available) - callers no longer pass auth headers themselves, the same effect the old `apiFetch` had, just centralized once instead of per call. RFC 9457 problem-detail parsing (`zod`, permissive - every field optional, since this client doesn't control that shape and a slightly-off problem body should still produce a readable error) mirrors `apps/loot-bot`'s own `toApiError`, translating a non-2xx result into the existing `ApiError` class. A shared `unwrap()` helper wraps every `client.GET/POST/PUT/PATCH/DELETE` call's `{ data, error, response }` result into either the resolved data or a thrown `ApiError` - centralized here (unlike `apps/loot-bot`'s own client, which repeats that check once per method) because this client only ever has this one module as a caller; `apps/loot-bot`'s doesn't have that luxury (many bot commands, several with their own error-handling wrinkles).

### `lib/types.ts` becomes thin aliases, not hand-maintained duplicates

Every interface that mirrored an `apps/api` response shape (`CatalogItem`, `ItemInstance`, `TenantSummary`, `CharacterSummary`, `BeingSummary`, `OwnedByResponse`, `PrototypeAncestor`, `BulkResultItem`, etc.) is now a type alias onto the generated `components['schemas'][...]` types, kept under its existing name so no `.astro` page's own imports needed to change. `Page<T>` stays hand-written: the schema generates one concrete `Page_<Schema>_` type per `T` rather than a reusable generic, and its own shape (`items`/`total`/`page`/`size`/`pages`) is stable, low-risk boilerplate untouched by a backend field rename - the risk this ADR is actually about doesn't apply to it. `BulkResultItem` is one alias covering both `BulkAssignResultItem` and `BulkMoveResultItem`, which the API generates as two structurally-identical schemas (this app already treated them as one shape before codegen; nothing here forces a copy per endpoint that happens to look the same).

### Every `lib/*.ts` API-calling module rewritten against the typed client

`items.ts`/`beings.ts`/`characters.ts`/`tenants.ts`/`me.ts` (and `debug/me.astro`'s own direct call) call `client.<METHOD>(path, { params, body })` instead of building a path string by hand, then `unwrap()` the result. Behavior is unchanged, including `listCatalogItems`/`listItemsUsingPrototype`'s own pre-existing first-page-only pagination gap ([ADR-worthy in its own right, tracked separately](https://github.com/ramsesoriginal/lorenzo/pull/116) rather than folded into this change).

## Not in scope

**Regenerating `lorenzo-schema.d.ts` from a local `apps/api` dump for this initial commit.** [PR #140](https://github.com/ramsesoriginal/lorenzo/pull/140)'s copy was generated from the *deployed* API's live `/openapi.json` (the same backend this app talks to by default, and public information the same way `API_BASE_URL` itself already is) rather than a local dump, since installing `apps/api`'s full Python toolchain wasn't otherwise needed for a frontend-only change. The `generate-client` script itself still points at the local-dump convention (`../api/openapi.json`) for every regeneration after this one.

**Extending this to `apps/account-hub`**, which has its own identical hand-rolled `apiFetch<T>` (`lib/api.ts`) and would benefit from the same change. A different app, owned separately - not folded into this ADR or its implementation.

**Writing the ADR before the code**, this once. Flagged in Context, not repeated here as a future intention - the point of recording it is that it shouldn't happen again, not that this document fixes it retroactively.

## Consequences

- New dependencies: `openapi-fetch` (runtime), `openapi-typescript` (dev), `zod` (runtime, problem-detail parsing) - all already precedented by `apps/loot-bot`'s own `package.json`.
- A `git diff` on this PR is large (every network call in the app rewritten) but mechanical - the same shape repeated per function, not a redesign of any single call's own behavior.
- A path typo, a removed/renamed response field, or a request body that no longer matches `apps/api`'s own schema is now a build-time (`astro check`/`tsc`) error in `apps/inventory-web`, not a runtime one discovered by hand - the concrete problem this ADR exists to close.
- Regenerating the client (`pnpm run generate-client`) needs a local `apps/api` OpenAPI dump (`mise run //apps/api:openapi-schema`) going forward, the same extra step `apps/loot-bot` already requires after any `apps/api` schema change; nothing currently fails CI if the two drift, the same gap [PR #118](https://github.com/ramsesoriginal/lorenzo/pull/118) addresses for `apps/loot-bot` (open, not yet merged, at the time of this ADR) - worth the identical fix here once that pattern is proven there, not built speculatively now.
