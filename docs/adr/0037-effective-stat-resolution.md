# 0037 - Effective stat resolution over the prototype graph

Status: accepted

## Context

[RFC 0001](../rfcs/0001-core-domain-data-model.md) decided the resolution *rule* in full: "more specific wins — a value defined closer to the entity... beats one defined further out, and an instance-level override always beats anything inherited... the tie breaks on `stat_group.priority`." [ADR 0015](0015-entity-prototype.md) built the graph this walks (`entity_prototype`, cycle-rejecting on write) but explicitly deferred the walk itself. Nothing since has built it: `v_item`/`v_item_instance` ([ADR 0019](0019-item-and-v-item.md)) read `entity_stat` for one entity's own id only, so an item that only inherits a stat (never sets it directly) shows `NULL` for it today.

GitHub milestone #1's scenario needs "Ashfang" (an instance) → "Flaming Sword" (a prototype) → "Sword" (a base prototype) to resolve as one coherent effective stat set, and needs moving Ashfang between containers to leave its resolved stats unchanged. Checking that scenario against every proposed RFC also surfaced a second, adjacent gap: there is no way to *write* `entity_stat`/`stat_definition`/`stat_group` at all. [RFC 0008](../rfcs/0008-effective-stat-resolution.md) named both gaps but deliberately left the mechanism, and the write endpoints' shape, undecided. This ADR accepts RFC 0008 and resolves both.

## Decision

### Resolution mechanism: a recursive CTE embedded directly in `v_item`/`v_item_instance`

Chosen over a Postgres function or an application-level Python walk (RFC 0008's three named options), for the reason the RFC itself flagged as most consistent with this codebase's existing pattern: `v_item`/`v_item_instance` already require `security_invoker = true` for RLS to apply (ADR 0019); a `SECURITY INVOKER` Postgres function would need the identical care and adds a second kind of database object to keep in sync with migrations, while an application-level walk would need to bypass the views entirely - a bigger change than RFC 0008's own text called this piece out to be. A recursive CTE inside the view's own `CREATE VIEW` SQL keeps every existing RLS/`security_invoker` property automatically, touches nothing outside the view migration, and mirrors `entity_prototype`'s own cycle-check trigger and `entity_access.recursive_descendants_cte`'s already-proven recursive-CTE shape in this codebase (`routers/item_instances.py`/`entity_access.py`), even though that one walks `containment`, not `entity_prototype`.

Migration `6341fedbfc47` replaces both `CREATE VIEW` statements from `6c2f0a9d3e17` ([ADR 0019](0019-item-and-v-item.md)). The views' plain-column *shape* is unchanged - same columns, same names, same `LEFT JOIN`-per-stat-name outer structure - only what populates `weight`/`height`/`price`/`rarity`/`hp`/`armor`/`is_magical`/`is_cursed` changes, per RFC 0008's own scope. Per view, three CTEs:

1. **`stat_ancestor(root_entity_id, ancestor_id, hops)`** - starting from every entity in the view's own source table (`item` or `item_instance`) as its own hop-0 ancestor, walks `entity_prototype` outward (`ep.entity_id = sa.ancestor_id` → `ep.prototype_id`, `hops + 1`) up to a depth bound of 50 (mirrors `entity_access.py`'s `_MAX_CONTAINMENT_DEPTH`). `entity_prototype`'s own `BEFORE INSERT` trigger ([ADR 0015](0015-entity-prototype.md)) already makes a cycle in this graph impossible by construction, so the depth bound here is a pure performance/pathological-depth safeguard, not something correctness depends on - unlike `entity_access.py`'s containment walk, which needs its own path-array cycle guard because `containment` is deliberately cycle-*tolerant* ([ADR 0016](0016-containment.md)).
2. **`ancestor_priority(entity_id, priority)`** - for every entity, the highest `stat_group.priority` among the stat groups it has itself acquired via `entity_stat_group` (`MAX(sg.priority) GROUP BY esg.entity_id`). See the tie-break note below for why this, not `stat_definition`'s own group, is what has to vary per ancestor.
3. **`resolved_stat(entity_id, stat_definition_id, value_int, value_text, value_float, value_bool)`** - `SELECT DISTINCT ON (root_entity_id, stat_definition_id) ... ORDER BY root_entity_id, stat_definition_id, hops ASC, COALESCE(priority, 0) DESC, ancestor_id`, joining `stat_ancestor` to `entity_stat` (only ancestors that actually set the stat produce a row at all) and `ancestor_priority`. Hop 0 (the entity's own direct value) always sorts first regardless of priority, giving "the entity's own direct `entity_stat` row always wins outright" for free from the `ORDER BY`'s column order, not a special-cased branch.

Each of `v_item`/`v_item_instance`'s eight named-stat `LEFT JOIN`s (`_resolved_stat_join`) now reads from `resolved_stat` filtered by `stat_definition.name`, instead of straight from `entity_stat` - otherwise byte-for-byte the same per-name join shape `6c2f0a9d3e17` already used.

### Resolving the priority tie-break, precisely

RFC 0001 says the tie between two equally-close ancestors "breaks on `stat_group.priority` — the value acquired through the higher-priority stat group wins," and leaves the actual query as an implementation detail. Read literally as "the priority of the stat's own group," this can never actually discriminate anything: `stat_definition` has a `UNIQUE(tenant_id, name)` constraint, so there is exactly one canonical `stat_definition` row per stat name per tenant, with exactly one `stat_group_id`. Two different ancestors both setting the *same* stat (e.g. two prototypes each giving a value for "durability") necessarily reference that one shared `stat_definition_id`, so "the stat's own group's priority" is identical for both candidates by construction - it is not a fact that varies per ancestor, so it cannot break a tie between them.

The priority that *does* vary per ancestor is which stat groups that specific ancestor entity has itself acquired via `entity_stat_group` ([ADR 0014](0014-stats.md)'s "entities and prototypes acquire stat groups" mechanism). This ADR reads "the value acquired through the higher-priority stat group wins" as being about *that*: when two ancestors are tied on hop-distance, the one whose own highest-priority acquired stat group outranks the other's wins, independent of which (shared, fixed) group the specific stat being resolved happens to live in. An ancestor with no acquired stat group at all defaults to priority `0` (`stat_group.priority`'s own column default). If two ancestors are *still* tied after that (equal hops, equal priority, or both/neither has any acquired group), `ancestor_id` is the final, deliberately arbitrary but deterministic tie-break - not specified further by RFC 0001, and not worth inventing a fourth criterion for without a concrete case that needs it.

This is a genuine interpretation call this ADR is making, not a restatement of something RFC 0001 already pinned down - flagged here explicitly since a future reader might reasonably have expected the other reading.

### Not resolved by this change: `EntityViewMixin`'s stat-group-listing properties

`physical_stats`/`economic_stats`/`destroyable_stats`/`damaging_stats`/`tags` (`models/entity_view_mixin.py`) and `GET /entities/{id}`'s own `stats` field walk `Entity.stats` directly - an entity's own direct `entity_stat` rows only, no inheritance. RFC 0008's text scopes this change to "only what populates `weight`/`hp`/`armor`/etc. changes" (the views' named columns specifically), not this second, independent read path. Left as-is: an item that inherits "weight" through a prototype now shows the correct resolved value in `ItemOut.weight`, but that same inherited value still will not appear in `ItemOut.physical_stats` (which only lists what's set *directly*) unless the entity also has its own direct row. This is a real, known inconsistency between the two read paths, not an oversight - fixing it would mean redesigning `EntityViewMixin`'s properties around the same resolution mechanism, which is a bigger, separate change than this RFC scoped for itself.

### Writing stats

Two new routers, split by authorization tier exactly as RFC 0008 named them:

**`routers/stats.py`** - `stat_group`/`stat_definition` CRUD, tenant-admin tier (`get_tenant_context`, unchanged from [ADR 0032](0032-item-and-item-instance-crud-api.md)'s identical item-catalog reasoning: authoring the shared stat vocabulary is the same kind of concern as authoring the item catalog). `POST /tenants/{tenant_id}/stat-groups` (`StatGroupCreate{name, priority=0}`) and `POST /tenants/{tenant_id}/stat-definitions` (`StatDefinitionCreate{name, stat_group_id, value_type}`, `422 InvalidStatGroupError` if `stat_group_id` doesn't resolve in this tenant - mirrors `InvalidItemPrototypeError`'s own body-reference-validation shape), each `201` + `Location` + a `GET /stat-groups/{id}` / `GET /stat-definitions/{id}` canonical shape (added specifically so `POST`'s `Location`/canonical-`GET` convention has something to point at - RFC 0008 only asked for "at minimum... creating," but ADR 0032's cross-cutting convention needs a `GET` to exist at all). No list/`PATCH`/`DELETE` for either - not asked for, not built; a future RFC can add them the same way item CRUD's own list/update/delete were added once actually needed. Neither route needs `dependencies.set_tenant_rls_context`'s post-commit re-arm ([ADR 0032](0032-item-and-item-instance-crud-api.md)) - unlike `create_item`, nothing here re-queries through a `security_invoker` view after the commit; the response is built from the same in-memory row the commit just persisted, kept readable by `async_session_factory`'s `expire_on_commit=False` ([db.py](../../apps/api/src/lorenzo_api/db.py)).

**`routers/entity_stats.py`** - `PUT /tenants/{tenant_id}/entities/{entity_id}/stats/{stat_definition_id}` (`SetEntityStatRequest{value: int | str | float | bool}`), self-or-managed tier, gated by `get_tenant_or_404` at the router level (mirrors `routers/item_instances.py`'s identical reasoning: a plain `Player` doesn't imply tenant-wide `Membership`, ADR 0022) with its own explicit `_authorize_entity_stat_write` check per request. That check is `routers/item_instances.py`'s `_authorize_instance_write` generalized from "an item instance" to "any entity": self-service via `entity_access.can_self_manage_entity` (this already covers a player setting their *own* character's stats directly, not only their owned items - a controlled character is itself one of `reachable_entity_ids`' own roots, not something reached *through* it); otherwise, if the entity is `Ownership`-owned by some character, that owner's own campaign(s) need `can_manage_campaign`; an entity with no owner at all (a catalog prototype like "Sword" or "Flaming Sword" - never owned by anyone, only ever prototyped-from) falls back to `can_manage_any_campaign_in_tenant`. That fallback is what makes setting a stat on a bare catalog item reachable at all through this single, generic endpoint: `can_manage_any_campaign_in_tenant` is satisfied by tenant `OWNER`/`ORGA` unconditionally (`campaign_access.is_tenant_admin`), regardless of whether any campaign yet exists - the same tenant-admin-shaped caller `items.py`'s own tenant-admin tier already serves reaches this tier's fallback branch too, without a second, separate "is this a catalog item" check.

`value`'s Python type is checked against the target `stat_definition.value_type` exactly (`_validate_value_type`; `bool` checked before `int`, since Python's `bool` is an `int` subclass) - `422 InvalidStatValueTypeError` on a mismatch, with no `int`↔`float` coercion. This is the application-level check [ADR 0014](0014-stats.md) named as a known gap ("*which* [value column] should be set... isn't enforced by the schema... left to application code for now") - now built, rather than leaving a bad type to surface as an opaque DB `CHECK` violation.

The route returns `EntityDetailOut` (`routers/entities.py`, extracted into a reusable `get_entity_detail_or_404` so this router shares the exact eager-load chain instead of a second, drifting copy - mirrors `routers/items.py`'s `eager_load_options` already being reused by `routers/item_instances.py`), not an `ItemOut`/`ItemInstanceOut`: this write is entity-generic (a character's `hp`, an item's or item-instance's `weight`, a bare catalog prototype's own base value), so there is no single item/item-instance-shaped canonical resource for it to return - `GET /entities/{id}`'s own existing shape already is the canonical shape for "an entity," reused as-is.

Check order in the route: `entity` existence (404) → `stat_definition` existence (404) → authorization (403) → value-type validation (422) → `If-Match` (412, checked against the `entity_stat` row's own `updated_at` if one already exists - not `entity.updated_at`, since a stat-setting write is not "updating the entity" in [ADR 0029](0029-attribution-created-by-updated-by.md)'s attribution sense, and because `entity_stat` may not exist yet at all for a first-ever set, unlike `Entity`, which is always already there by the time `routers/item_instances.py`'s own writes check `If-Match`). A first-ever set always succeeds regardless of any `If-Match` header sent - there is no prior version for it to have gone stale relative to.

`stat_group`/`stat_definition`/`entity_stat` still get no `created_by`/`updated_by` ([ADR 0029](0029-attribution-created-by-updated-by.md)'s explicit deferral, unchanged by this ADR) - and `entity_stat_group` acquisition is not required or auto-created by this write endpoint; setting a value for a stat an entity hasn't "acquired" the group for remains possible and unenforced, the same known, already-documented gap [ADR 0014](0014-stats.md) left open.

New typed problems (`exceptions.py`): `StatGroupNotFoundError`/`StatDefinitionNotFoundError` (404), `InvalidStatGroupError`/`InvalidStatValueTypeError` (422), `EntityStatManagementForbiddenError` (403).

## Not in scope

Everything RFC 0008 itself left open and didn't ask this ADR to resolve: caching/materializing effective stats (live computation stays the default), `game_system` becoming a real modeled concept, multi-game-system stat scoping (RFC 0001's open question #3). Also not built: `stat_group`/`stat_definition` list/update/delete, and an `entity_stat` read/delete endpoint beyond what `GET /entities/{id}` and `PUT .../stats/{id}`'s own response already surface - none of these were asked for by "at minimum" scope, and speculative CRUD completeness isn't this codebase's practice (see AGENTS.md).

## Consequences

- No schema migration for the write endpoints - `stat_group`/`entity_stat_group`/`stat_definition`/`entity_stat` already exist exactly as both halves of this ADR need them ([ADR 0014](0014-stats.md)). One migration for resolution (`6341fedbfc47`), replacing both views' `CREATE VIEW` statements; `downgrade()` inlines the original pre-resolution SQL rather than importing it from `6c2f0a9d3e17`, so this migration stays a self-contained snapshot independent of that file's own helpers ever changing.
- `ItemOut.weight`/`hp`/`armor`/etc. (and the equivalent `ItemInstanceOut` fields) now reflect inherited values, not just an entity's own direct ones - the real, previously-shipping gap RFC 0008's own Context section named is closed. `ItemOut.physical_stats`/`tags`/etc. do not reflect inheritance and can now visibly disagree with the resolved top-level fields for the same underlying stat (see above) - a known, accepted scope limit, not a bug to be quietly patched later without deciding to.
- The `ancestor_priority`-based tie-break reading is a real interpretation call, not something RFC 0001 fully pinned down; revisit if a concrete scenario ever needs the tie-break to key off something else (e.g. the specific inheritance edge, which the schema doesn't currently record any per-edge information about at all).
- `routers/entities.py:get_entity_detail_or_404` is now a second consumer's shared helper, not a one-off inline query - the same "generalize once a second caller appears" pattern `entity_access.py`'s own extraction already followed (ADR 0032).
- Setting a stat on a bare catalog prototype (no owner, no character) and setting one on a live instance go through the exact same endpoint and the exact same authorization function - deliberate, per RFC 0008's own single "self-or-managed" framing, rather than splitting catalog-stat-writes off into `routers/stats.py`'s tenant-admin tier the way item *catalog* CRUD itself is split from item *instance* CRUD. Revisit if that turns out to be too permissive in practice (e.g. if authoring catalog stats should require tenant-admin specifically, not merely "manages some campaign").
