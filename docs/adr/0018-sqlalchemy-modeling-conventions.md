# 0018 - SQLAlchemy modeling conventions: type map, relationships, cascades

Status: accepted

## Context

Every model since [ADR 0012](0012-entity-table.md) used the same style: bare FK columns with no `relationship()`, explicit `mapped_column(Text, ...)`/`mapped_column(UUID(as_uuid=True), ...)` on every attribute, and no `ondelete` on any `ForeignKey`. This was adequate for building each sub-slice in isolation, but it's cost real time repeatedly: `test_stats.py`, `test_entity_prototype.py`, `test_containment.py`, and `test_information.py` all needed extra, hand-written `session.flush()` calls between deletes, because SQLAlchemy's unit of work has no `relationship()` to infer dependency order from bare FK columns alone.

Asked to research current SQLAlchemy 2.0 idiom rather than continue the ad hoc style, the relevant findings (verified against the official docs and, where the docs were ambiguous, against this project's own real Postgres instance rather than assumed):

- **`relationship()` + `back_populates` is the modern default**, not an optional extra - the legacy `backref` parameter is documented as legacy. `relationship()` isn't strictly required for a FK to work, but it's what unlocks correct unit-of-work delete ordering, which is exactly the gap that kept costing us manual flushes.
- **Bare `Mapped[X]` (no `mapped_column()` call) is standard** for a column needing no special configuration - confirmed empirically (`CreateTable(...).compile()`) that `Mapped[uuid.UUID]` already produces a native `UUID`/`Uuid` column with no dialect-specific import needed, and `Mapped[decimal.Decimal]` already produces `NUMERIC`, matching what we hand-wrote before. `Mapped[str]` defaults to `VARCHAR`, not `TEXT`, and `Mapped[datetime]` defaults to a timezone-*naive* `TIMESTAMP` - both confirmed the same way. A table's own `type_annotation_map` (set once on `Base`) can override these per-project defaults, letting every model use bare `Mapped[str]`/`Mapped[datetime]` and still get `TEXT`/`TIMESTAMPTZ`, matching what every migration so far already hand-specified.
- **Database-level `ForeignKey(..., ondelete="CASCADE")` and ORM-level `relationship(cascade="all, delete-orphan")` are meant to be combined**, not chosen between - the DB level makes deletes correct even when they don't go through the ORM (or through a client using a non-superuser role, relevant to our still-open RLS gap - [ADR 0002](0002-multi-tenancy-shared-schema-rls.md)/[0012](0012-entity-table.md)); the ORM level keeps in-memory session state consistent. `passive_deletes=True` tells SQLAlchemy to let the database cascade rather than first `SELECT`-ing every child row to delete it one by one.
- **Alembic's autogenerate does not reliably detect `ondelete` changes on existing foreign keys** (confirmed against multiple independent SQLAlchemy/Alembic issue reports, consistent with this project's own experience that autogenerate is diff-based on structure it actively compares) - adding `ondelete="CASCADE"` to already-migrated tables needs a hand-written migration that drops and recreates each affected constraint, verified afterward by confirming a fresh autogenerate run finds zero remaining diff.
- **A self-referential relation through an association *class*** (not a plain secondary table) with two distinct FKs to the same parent table - our exact shape for `entity_prototype` and `containment` - needs `foreign_keys=` on each `relationship()` to disambiguate which FK column it travels through; mixing this pattern with a `secondary=` convenience relationship on the parent risks reading/writing inconsistent state per the docs, so none of our association tables get one. Verified directly (not assumed) with a throwaway two-FK self-referential model against this project's real Postgres instance before applying it project-wide: correct disambiguated navigation both directions, and `ondelete="CASCADE"` correctly removing only the edge row (never the referenced `Entity`) when either endpoint is deleted.

## Decision

Applied project-wide, to every model in `apps/api/src/lorenzo_api/models/`:

1. **`type_annotation_map` on `Base`** (`db.py`): `str -> Text`, `datetime -> DateTime(timezone=True)`. `uuid.UUID` and `decimal.Decimal` need no override - their built-in defaults already match what every migration so far hand-specified.
2. **`Annotated` column aliases** for the three patterns repeated in nearly every table: a UUID primary key with `gen_random_uuid()`, a `tenant_id` foreign key (indexed, `NOT NULL`, `ondelete="CASCADE"`), and the `created_at`/`updated_at` timestamp pair. Defined once, reused everywhere a plain FK/PK doesn't need per-table customization.
3. **`relationship()` + `back_populates` on every FK relevant to actual navigation**, with `cascade="all, delete-orphan"` and `passive_deletes=True` on the owning side. Every table in this schema represents genuine composition (an `entity_stat` row has no meaning without its `entity`, a `payload_description` row has no meaning without its `payload`, and so on) - nothing here is a shared reference that should outlive its parent, so cascade is applied uniformly rather than case-by-case. `Tenant` itself only gets `entities`/`stat_groups`/`stat_definitions` back-populated collections, matching the same restraint the [merged ER diagram](../architecture/diagrams/domain-model-er.md) already uses (only entity-anchored or independent-top-level tables get an explicit tenant-scoping edge drawn) - the other nine tables' `tenant_id` stays a plain column, present for RLS, not surfaced as an ORM navigation path.
4. **`ForeignKey(..., ondelete="CASCADE")` on every FK**, including `entity_prototype`'s and `containment`'s two self-referential columns - deleting an `Entity` on either side of one of these edges removes the edge row, never cascades into deleting the *other* `Entity`.
5. **`from __future__ import annotations`** in every model file, enabling plain `Mapped[Entity]`/`Mapped[Entity | None]` cross-file forward references without quoting them as strings.

**Revised after initial acceptance**: the first version of this ADR stopped at association-object access only (e.g. `entity.stat_group_links[i].stat_group`), with no `secondary=`-style convenience relationships at all, reasoning that mixing them with the association-object mapping our join tables already use risks inconsistent reads/writes. Asked for exactly these convenience accessors (`entity.stat_groups`, `entity.prototypes`, `entity.instances`, `entity.parent`, `entity.children`), the actual SQLAlchemy documentation's own mitigation for this is `viewonly=True` on the `secondary=` side - not avoiding it altogether - so `Entity` now has all five, each `viewonly=True`. Verified directly (not assumed) with a throwaway proof-of-concept mirroring `entity_prototype`'s exact shape before applying it for real: reads return the correct target `Entity`/`StatGroup` objects (not join rows), and attempting to mutate through one of these (e.g. `entity.prototypes.append(...)`) never persists a row - confirmed empirically rather than trusted, since a silent phantom write (missing `tenant_id`) would be worse than no write path at all. Writes still only ever go through the association-object relationships (`stat_group_links`, `prototype_links`/`dependent_links`, `containment`/`contained_links`) or the association classes directly.

## Consequences

- The `session.flush()`-between-deletes workarounds in `test_stats.py`, `test_entity_prototype.py`, `test_containment.py`, and `test_information.py` are no longer needed and are removed - `relationship()` gives the unit of work real dependency ordering, and `passive_deletes=True` lets the database's own `ON DELETE CASCADE` finish the job without SQLAlchemy first loading every child collection.
- **Deleting a `Tenant` now cascades through every table that (transitively) references it** - the most consequential instance of the "cascade uniformly" rule above. Acceptable now because no tenant-deletion API exists yet and this is still an unreleased branch; revisit before any real deletion endpoint ships if a softer/guarded delete is wanted instead.
- A hand-written migration (not autogenerate, for the reason above) adds `ON DELETE CASCADE` to every existing foreign key constraint; verified by confirming a subsequent `alembic revision --autogenerate` finds no remaining diff against the updated models.
- Same RLS-superuser caveat as every table so far, now doubly relevant: DB-level cascade means a delete against this schema behaves consistently whether or not it went through the ORM or a properly-restricted role, which is exactly the case the superuser gap ([ADR 0002](0002-multi-tenancy-shared-schema-rls.md)/[0012](0012-entity-table.md)) still doesn't cover for reads/writes generally.
- `entity.stat_groups`/`prototypes`/`instances`/`parent`/`children` are `viewonly=True` for a reason, not an oversight - attempting `entity.prototypes.append(...)` fails (confirmed: nothing persists), but the failure surfaces as an unrelated-looking async/greenlet error rather than a clear "this relationship is read-only" message. Anyone hitting that error on one of these five attributes specifically should look here first rather than assume it's a new bug.
