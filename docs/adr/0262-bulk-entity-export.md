# 0262 - A bulk entity export, with a revision for an ETag

Status: accepted. Slice W3 of [RFC 0039](../rfcs/0039-bench-authoring-offline-and-extensibility.md) (section 6), tracked in #498. Builds on [ADR 0002](0002-multi-tenancy-shared-schema-rls.md) (tenant rows), [ADR 0028](0028-knowledge-and-group-membership.md) and [ADR 0109](0109-player-knowers-knower-listing-and-information-list.md) (what a caller may read of an entry's information), [ADR 0042](0042-concurrency-token-on-reads.md) (`ETag`), [ADR 0225](0225-stat-writes-that-can-be-checked-and-undone.md) (an entry's version moves with its stats) and [ADR 0229](0229-parents-in-the-entry-list.md) (parents without reading each entry).

## Context

A mirror of a repository on today's API is one request for the names and then one `GET .../entities/{id}` per entry, and that read gives stats by name as effective values, with no definition ids, so it holds less than a write needs (RFC 0039 section 6). Bench's offline foundation (B4) needs the whole repository in a few requests, a way to ask "has anything changed" that costs one cheap answer, and pages that fit together. The B0 spike measured a repository the size of the importer's standard equipment (700 entries) at about 0.9 MB raw and 210 to 230 KB gzipped, and ten times that at 2 MB gzipped, so full refetch behind an `ETag` is workable and a delta feed stays deferred.

What the `ETag` is was the open question. Nothing records a deletion, three content tables have no timestamp (`entity_prototype`, `entity_slug`, `entity_stat_group`), and a stat or a payload moves its own row's version, so a maximum of `updated_at` over some rows misses a deletion and a change of parents.

## Decision

### The endpoint

`GET /tenants/{t}/entities/export?limit=&cursor=`, open to whoever may open `GET .../entities` (a tenant participant), registered before `/{entity_id}`.

- **Cursor pages, id order.** `limit` is 1 to 500 (default 200). The page is `{ revision, items, next_cursor }`; `next_cursor` is null on the last page. The order is the entry id, not the name: a stable key that does not move when a name does, and the client sorts. The cursor is opaque (base64 of the token the export began with and the last id returned); one this API did not give out is `422`.
- **One entry (`EntityExportOut`)**: `id`, `name`, `slug` (the link name), `kinds`, `parent_ids`, `stat_group_ids`, `stats` (the values the entry holds itself, `{ stat_definition_id, value, updated_at }`, a tag being a bool; nothing inherited and nothing computed), `information`, `created_at`, `updated_at`. `information` is `InformationOut` as `GET .../entities/{id}` gives it, with picture and document payloads as a `url` and `file_type`, never as bytes (the main picture is the information of type `main_picture`). `updated_at` is the entry's `ETag` and `If-Match` for a write; a stat's own `updated_at` is the stat's.
- **Left out**, deliberately: effective and computed values (the mirror computes them, RFC 0039 section 4), formulas (`computed_stat`, B7 will ask for them), the stat vocabulary (`stat_definition`, `stat_group` and their enum values have their own reads), containment and ownership (play-tenant structure; a repository has neither), and the entry's `instances` and `children` (derivable from `parent_ids`).
- **What the caller may read is what the single read shows.** Information is filtered by `visible_information_clause`, the SQL form of the rule `GET .../entities/{id}` applies in Python (ADR 0109, which has a parity test). A caller never gets a row they could not read one by one; a test compares the export with the single read for the owner, a plain participant, and a participant whose character knows one restricted row. Every entry is listed for every participant, as `GET .../entities` does.
- **Errors**: `409` for a cursor whose export has changed (below), `422` for an invalid cursor or limit, `404` for a tenant the caller has no standing in.

### The revision and the `ETag`

- **`tenant.export_revision`, a counter on the tenant row, moved by deferred constraint triggers.** An `AFTER INSERT OR UPDATE OR DELETE ... FOR EACH ROW` constraint trigger, `DEFERRABLE INITIALLY DEFERRED`, on each table the export shows: `entity`, `item`, `item_instance`, `being`, `character`, `entity_slug`, `entity_prototype`, `entity_stat`, `entity_stat_group`, `information`, `payload`, `payload_description`, `payload_number`, `payload_picture`, `payload_document` and `knowledge` (which decides who reads a row). The function adds one to the tenant's counter the first time any of them fires **in a transaction** (a transaction-local setting remembers it, and a rollback to a savepoint forgets it with the update), so a transaction that writes 7,000 entries bumps once. Deletions are covered because a trigger sees them, and so are the tables without a timestamp; a cascade from a deleted entry fires the triggers of its children.
- **Why deferred: the cost under concurrent writers.** Writers in one tenant do contend on one row, which is the cost RFC 0039 named. A trigger that ran at the end of each statement would take the tenant row at the first write and hold it to the end of the transaction, and two transactions writing the same two entries in opposite orders would then deadlock on a lock the second statement did not need to take (A holds the counter and waits for the entry B wrote; B waits for the counter). Deferred to commit, the row is taken after every other lock of the transaction is already held, for the length of the commit alone: no new deadlock, and the contention is a queue of commits each a few milliseconds long. A test holds two transactions open on different entries and commits them in turn within a timeout. It was not measured under load; the B0 numbers were for a stub. If the row ever hurts, the counter can become one row per shard, summed on read, without a change to the API.
- **The `ETag` is the revision joined to a digest of the caller's visibility**: `W/"<revision>.<digest>"`, the digest being of the sets `resolve_information_visibility` returns (admin bit, players, characters and groups known, GM reach). What a caller reads depends on ownership, containment, groups and campaigns, which no trigger of ours watches; folding the resolved sets in makes a change to what the caller may read a different token without a trigger on every table behind it, and keeps two callers who read differently from sharing one. It costs the visibility queries on a `304` too, a few short selects.
- **`If-None-Match`** (the weak comparison, a list, or `*`) on a request **without a cursor** with the current token answers `304` with the `ETag` and no body. On a page with a cursor it is not read: the client is asking for the next page, not whether it needs the first.
- **Consistent across pages.** The cursor remembers the token its export began with. A page whose token has since moved (a write, or a change to what the caller may read) is `409` and the client starts again; it never joins two halves of different states. The revision is read before the rows, so a write landing between leaves the token older than the data it labels, never newer: the next request asks again, and no mirror is kept a revision ahead of what it holds.
- `ETag`, `Cache-Control: private, no-cache` (the response is per caller) and, when compressed, `Vary: Accept-Encoding` are on every page.

### Compression

Nothing in the API compressed responses, and what sits in front of it is not known. Starlette's `GZipMiddleware` is applied, through a small wrapper (`compression.py`), **to paths ending in `/entities/export` only**: it honours `Accept-Encoding`, sets `Content-Encoding` and leaves a client that does not ask alone. The alternative, compressing every JSON response, is one line more and was left out: pictures are already compressed, most responses are small, and the one measured need is this one. An edge that compresses as well is harmless (a response already encoded is not encoded twice).

## Consequences

- A migration: `tenant.export_revision bigint not null default 0`, one trigger function, sixteen triggers. Every write to those tables costs one deferred trigger event per row, which is a cheap no-op after the first in a transaction. No new tenant table, so nothing for `copyable_tables.py`; a library that copies a repository gets its own revision from the rows the copy writes.
- A new tenant table that the export shows needs a trigger in its migration; a test lists the tables that carry one, so the list changes in two places on purpose.
- The revision moves on writes the export does not show (a no-change `UPDATE` of a row, `updated_at` bookkeeping), so a mirror sometimes refetches for nothing. The alternative, comparing old and new rows in the trigger, was not worth its cost.
- `409` on a long export during active editing means a client may restart; with a repository a few hundred KB gzipped that is cheap, and it is the case the delta feed (still deferred) would remove.
- The generated TypeScript schema gains the route and its schemas.
