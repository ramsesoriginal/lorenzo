# Architecture overview

## Components

Every deployable app lives under `apps/`, one directory per app, named by purpose rather than type — see [ADR 0007](../adr/0007-apps-layout-and-multiplicity.md). `apps/api`, `apps/loot-bot`, `apps/inventory-web`, and `apps/account-hub` exist so far. `apps/api`'s full domain model — the entity/component core (stats, prototypes, containment, information/payloads, item/item_instance, [ADR 0012](../adr/0012-entity-table.md)-[0019](../adr/0019-item-and-v-item.md)) plus tenant/user/membership, campaign/player, character/ownership, and campaign GM/orga ([ADR 0021](../adr/0021-restricted-app-role-for-rls-enforcement.md)-[0026](../adr/0026-campaign-gm-orga-and-access-rule.md)) plus a dedicated `character` table ([ADR 0031](../adr/0031-character-table-and-read-api.md)) — a REST API covering full CRUD for tenants, memberships, campaigns (incl. GM grants and admin opt-out), players, characters, items/item-instances, entity stats, and information/payload/knowledge — its write surfaces ([ADR 0032](../adr/0032-item-and-item-instance-crud-api.md)/[0033](../adr/0033-tenant-creation-and-update-api.md)/[0034](../adr/0034-campaign-crud-api.md)/[0036](../adr/0036-user-player-character-crud-api.md)/[0037](../adr/0037-effective-stat-resolution.md)/[0038](../adr/0038-information-payload-knowledge-crud-api.md)) — plus campaign-scoped GM visibility ([ADR 0035](../adr/0035-campaign-scoped-gm-visibility.md)) and Authgear-backed auth over all of it ([ADR 0020](../adr/0020-rest-api-tenant-scoping-and-schemas.md)/[0023](../adr/0023-authgear-token-verification.md)/[0027](../adr/0027-authgear-cloud-not-self-hosted.md)/[0030](../adr/0030-tenant-campaign-read-api.md)/[0031](../adr/0031-character-table-and-read-api.md)) both exist now - see the [domain model ER diagram](diagrams/domain-model-er.md).

| Component type | Role | Multiplicity |
| --- | --- | --- |
| Backend API | Source of truth. Multi-tenant REST API over PostgreSQL. | One — [`apps/api`](../../apps/api), full CRUD for tenants/memberships/campaigns/players/characters/items/item instances/entity stats/information/payloads/knowledge, plus auth (`/me`) |
| Web frontend(s) | Static UI for GMs/players (zero-JS by default). | [`apps/inventory-web`](../../apps/inventory-web) — GM item catalog/instance management, kanban-style container board; [`apps/account-hub`](../../apps/account-hub) — a user's own account: profile, notifications, tenant/campaign roster and admin, character/being management ([ADR 0004](../adr/0004-static-astro-frontend.md)/[0071](../adr/0071-account-hub-stack-auth-deploy.md)); possibly more later |
| Discord bot(s) | Talks to the API — e.g. loot/inventory. | [`apps/loot-bot`](../../apps/loot-bot) — Discord account linking, self-service inventory viewing/managing, loot-splitting, GM loot drops with claims, and item awarding ([ADR 0050](../adr/0050-loot-bot-stack-linking-and-isolation.md)/[0051](../adr/0051-loot-bot-give-command.md)/[0052](../adr/0052-loot-bot-loot-drop-and-claims.md)), deployed on Google Cloud Run over Discord's HTTP Interactions Endpoint rather than its Gateway ([ADR 0053](../adr/0053-loot-bot-http-interactions-and-cloud-run-deploy.md)); possibly more bots/apps later |
| Mobile app(s) | Talks to the API — narrower, audience-specific views. | Possibly more than one |

Everything other than the backend API is a *view* onto it — narrower, audience-specific slices of the same data, not a separate source of truth. See the [system context diagram](diagrams/system-context.md).

## Domain shape (why the data model will look the way it does)

The full picture — the layered world model, repositories, entities/knowledge/visibility, and how different client apps narrow all of it down — lives in [docs/domain](../domain), not here. This section is just the one-line technical summary: **where** something is (several independent, not-always-linear coordinate systems at once, not one hierarchy), **who knows what** (per-character, per-point-in-time, not global), and **who can see what** (every piece of text/stats split by audience).

The entity design itself is recorded in [RFC 0001](../rfcs/0001-core-domain-data-model.md) (the entity/component core) and [RFC 0002](../rfcs/0002-campaign-player-character-model.md) (campaign/player/character) — being built incrementally, smallest sub-slice first, starting with the bare `entity` table ([ADR 0012](../adr/0012-entity-table.md)). See the [domain model ER diagram](diagrams/domain-model-er.md) for how every table built so far actually connects.

## Cross-cutting concerns

- **Multi-tenancy**: [ADR 0002](../adr/0002-multi-tenancy-shared-schema-rls.md) — shared schema + PostgreSQL row-level security. The app's own connection is a restricted, non-superuser role RLS actually applies to ([ADR 0021](../adr/0021-restricted-app-role-for-rls-enforcement.md)), locally, in CI, and in production — the live Neon role rotation is done and confirmed (not just deployed: the restricted role's privilege flags and `FORCE ROW LEVEL SECURITY` were checked directly against production Postgres).
- **Observability**: health/readiness/metrics and structured (`structlog`) JSON logs exist in `apps/api` from its first commit, as intended, now correlated with `trace_id`/`span_id` from the active OpenTelemetry span, plus OpenTelemetry tracing itself (console exporter — no collector in this project's infra yet). See [docs/architecture/observability.md](observability.md) for what each signal actually covers and what isn't wired up yet.
- **Auth**: [ADR 0009](../adr/0009-identity-provider-authgear.md)/[ADR 0023](../adr/0023-authgear-token-verification.md)/[ADR 0027](../adr/0027-authgear-cloud-not-self-hosted.md) — Authgear Cloud as the identity provider, with real OIDC bearer-token verification built and required on every tenant-scoped route.
- **Deployment**: [ADR 0011](../adr/0011-deploy-target-cloud-run-neon.md) — Google Cloud Run + Neon, continuously deployed on every push to `main` that touches `apps/api/` (`.github/workflows/deploy-api.yml`). Confirmed working end to end (2026-09-09): a real login through production Authgear Cloud, a real token, verified against the live deployed Cloud Run service, correctly auto-provisioned a real `app_user` row via `GET /me`. `apps/loot-bot` shares the same Cloud Run/GCP project, but first needed its transport rewritten off the Discord Gateway onto Discord's HTTP Interactions Endpoint to fit Cloud Run's scale-to-zero model at all ([ADR 0053](../adr/0053-loot-bot-http-interactions-and-cloud-run-deploy.md), `.github/workflows/deploy-loot-bot.yml`) — its pipeline is wired up, pending the one-time GCP setup [docs/operations/deployment-setup.md](../operations/deployment-setup.md) also covers. See [docs/architecture/deployment.md](deployment.md) for the components and how they connect.

## Roadmap

This section is a historical, append-only build chronicle — what shipped, in order, each fact tied to the ADR that decided it. It is not where "what's in flight right now" lives; that's tracked live via GitHub Milestones/Issues (`gh issue list --state open`), not narrated here — see [ADR 0070](../adr/0070-planning-milestones-issues-and-a-deferred-roadmap.md) for why, and [What's next](#whats-next) below for the current pointer. Below this line, only add facts about what has *already landed* — never a status update about unfinished work.

Both vertical slices that were in progress earlier are built and merged to `main`: simple inventory management (entity/stats/information/payloads/prototypes/containment/item/item_instance, ADRs 0012-0019, plus a read-only REST API over all of it, [ADR 0020](../adr/0020-rest-api-tenant-scoping-and-schemas.md)) and auth/users/campaigns/GM (Authgear, User/Tenant/Membership, Campaign/Player, Character/ownership, Campaign GM/orga — ADRs 0009/0021-0026, RFC 0002 accepted), plus production Authgear Cloud wiring (ADR 0027) and per-character/per-group/public information visibility ([ADR 0028](../adr/0028-knowledge-and-group-membership.md)) on top.

The REST API surface that work left unbuilt was built on `feat/rest-api-surface`, now merged to `main`: tenant/campaign read endpoints, `is_tenant_admin`/`is_tenant_participant` ([ADR 0030](../adr/0030-tenant-campaign-read-api.md)), the new `character` table plus campaign-scoped roster routes ([ADR 0031](../adr/0031-character-table-and-read-api.md) — `campaign_access.can_access_campaign()` is wired to real routes now, not just built), item/item-instance CRUD — the first write surface, self-or-managed authorization, `entity_access.py`'s shared reachability walk, `If-Match`/ETag concurrency ([ADR 0032](../adr/0032-item-and-item-instance-crud-api.md)) — tenant creation gated by an Authgear role ([ADR 0033](../adr/0033-tenant-creation-and-update-api.md)), campaign CRUD including GM grants and the tenant-admin opt-out toggle ([ADR 0034](../adr/0034-campaign-crud-api.md)), campaign-scoped GM visibility reusing that same reachability walk ([ADR 0035](../adr/0035-campaign-scoped-gm-visibility.md)), effective stat resolution through the prototype graph plus stat CRUD ([ADR 0037](../adr/0037-effective-stat-resolution.md)), the full user/player/character write surface — `DELETE /me`, membership invite/role-change/revoke, player join/leave, and character create/promote/update/demote plus roster-link sub-resources, with a three-way "managed" authorization split ([ADR 0036](../adr/0036-user-player-character-crud-api.md)) — and information/payload/knowledge CRUD — description-payload authoring plus knower grant/revoke sub-resources, reusing that same self-or-managed shape a third time, and fixing two real gaps the milestone required: `GET /entities/{id}` was still Membership-gated, and `get_tenant_or_404` was silently losing RLS scoping under a genuine token across every router that used it ([ADR 0038](../adr/0038-information-payload-knowledge-crud-api.md)) — are all done. The milestone scenario - Oscar's tenant, Zorro's campaign, Xavier/Alice and Yvonne/Bob, the Sword→Flaming Sword→Ashfang prototype chain, ownership, containment, the public/character-specific/GM-only information split, and cross-tenant isolation - is now proven end to end in one continuous run through the real HTTP API, every actor on their own real verified JWT (`apps/api/tests/test_milestone_scenario.py`), not just piecewise across ADR 0032-0038's own narrower tests. Effective stat resolution now runs through one generic `v_effective_stat` view rather than being duplicated inside `v_item`/`v_item_instance` and limited to items - every entity (characters included) and every stat_definition resolves inheritance, and `EntityViewMixin`'s `physical_stats`/`tags`/etc. and `GET /entities/{id}`'s own `stats` field read through it too, closing the inconsistency [ADR 0037](../adr/0037-effective-stat-resolution.md) had flagged and left open ([ADR 0039](../adr/0039-generic-effective-stat-view.md)). Item-instance reads no longer show every character's inventory to any tenant participant - an owned instance is now visible only to whoever can reach its owner (self, GM, or `ORGA`), while ownerless instances stay open to all, closing a real cross-character privacy gap ([ADR 0040](../adr/0040-item-instance-read-visibility.md)). `Containment` now carries a `quantity` (default 1) - stacks of identical items, crowds of people, or any other fungible group of entities are one row apiece rather than one per unit, surfaced through `ItemOut`/`ItemInstanceOut.quantity` and `EntityDetailOut.quantity`/`children[].quantity` alike, plus a `POST .../item-instances/{id}/split` write endpoint for peeling part of a stack off ([ADR 0041](../adr/0041-containment-quantity-and-stacking.md)). Open design questions, not yet scoped into any RFC/ADR/issue: RFC 0001's redaction-alternative question (ADR 0028 built the authored-truths knowledge model; the "one truth, redacted per audience" alternative stays open), a finer per-tier information-authorization model than self-or-managed (flagged in ADR 0038 as deliberate, not resolved), and cross-tenant repositories ([docs/domain/repositories.md](../domain/repositories.md)). These are deliberately not tracked as issues — per [ADR 0070](../adr/0070-planning-milestones-issues-and-a-deferred-roadmap.md), an issue exists only for work a RFC/ADR has already decided, not for open questions nobody's picked up yet.

Further loot-management gaps reported against the above have since been closed: `If-Match` on item/item-instance writes was previously unusable in practice - nothing on the read side ever handed a client a token to send back. `ItemOut`/`ItemInstanceOut` now expose `updated_at`, and every read/write response for both also carries an `ETag` header derived from it, so a client can genuinely detect a concurrent write ("two players racing to take the same sword") instead of silent last-write-wins ([ADR 0042](../adr/0042-concurrency-token-on-reads.md)). Item instances can now carry an optional, tenant-unique `slug` (`ItemInstanceCreate.slug`/`ItemInstanceOut.slug`) resolvable via `GET .../item-instances/by-slug/{slug}` - a client authoring or scripting content can name a specific instance once and find it again later without already knowing its `entity_id` ([ADR 0043](../adr/0043-item-instance-slug.md)). Three loot-distribution primitives the motivating "loot drop" flow needed are done: `split` can hand the split-off piece straight to a different character in one call, `POST .../item-instances/{id}/merge` (split's own inverse, named as a real gap when ADR 0041 landed) folds a picked-up stack back into an existing one, and `POST .../item-instances/bulk-assign` resolves several already-decided assignments in one request with a per-item `"ok"`/`"error"` outcome rather than failing the whole batch on one stale claim ([ADR 0044](../adr/0044-loot-assignment-split-merge-bulk-assign.md)). `GroupMember` (ADR 0028) now has a read surface - `GET .../groups`, `GET .../groups/{id}/members`, and `GET .../characters/{id}/groups` - closing the "no way to browse groups to pick one as a knowledge-visibility target" gap with no write surface added ([ADR 0045](../adr/0045-read-only-groups-api.md)). A campaign's GM already saw GM-private information about anything their own players' characters own or carry (ADR 0035); that reachability walk now also starts from every entity that transitively contains one of those characters (the room a party is standing in, and so on up the containment chain), so a GM sees GM-private secrets about the scene their players are actually in - an NPC standing in the same room, a locked chest - not just their own inventory, with no new schema ([ADR 0046](../adr/0046-gm-reachability-widens-to-surroundings.md)). `GET /items` gains an optional `q` filter against the item's own name (not the nullable, description-sourced `title`); container-capability ("is this item usable as a container") needs no new field at all - it's documented as a tenant-defined boolean `stat_definition` (conventionally named `is_container`), already surfaced through the existing generic `tags` array with zero code changes ([ADR 0047](../adr/0047-item-catalog-search-and-container-convention.md)). CORS is configured (`CORSMiddleware`, origins from a new `CORS_ALLOWED_ORIGINS` setting, defaulting to none) so a static web frontend can actually call this API cross-origin, with `ETag`/`Location` explicitly exposed - both are load-bearing (ADR 0042/0032) but excluded from a browser's default cross-origin header safelist ([ADR 0048](../adr/0048-cors-configuration.md)). `GET /tenants/{tenant_id}/characters` gained a `mine` filter, narrowing to characters the caller's own `Player` rows own (not merely co-pilot) ([ADR 0049](../adr/0049-list-characters-mine-filter.md)).

A "rough tenant/user management" pass turned out to already be mostly built (campaign CRUD, GM grants, and Membership invite/role-change/revoke all landed with ADR 0034/0036) - the one real gap, closed on `feat/tenant-user-management`, was user identity itself: `User` held nothing but an Authgear subject id, so nobody could be invited by anything other than a `user_id` UUID only they could already see. `app_user` now carries an optional, globally-unique `email` (synced read-only from Authgear's own verified `email` claim at login, never written any other way) and an optional, globally-unique `nickname` (genuinely local, settable via a new `PATCH /me`) - the tenant roster (`GET /tenants/{id}/memberships`) surfaces nicknames too, so it's readable without a lookup per row ([ADR 0054](../adr/0054-user-identity-email-and-nickname.md) - renumbered past 0050-0053 on merge into `main`, which had independently claimed those numbers for loot-bot in the meantime). `GET /users/by-email/{email}` and `GET /users/by-nickname/{nickname}` resolve either, exact-match only, to the `user_id` the existing invite endpoints still take - open to any authenticated user, with no partial-match/search surface ([ADR 0055](../adr/0055-user-lookup-by-email-or-nickname.md)). Tenant deletion stays deliberately deferred (ADR 0033), unchanged.

Users, tenants, and campaigns can all now carry an uploaded profile picture (`PUT`/`DELETE /me/picture`, `.../tenants/{id}/picture`, `.../campaigns/{id}/picture`), bytes stored directly in Postgres via one shared `profile_picture` table plus three link tables - not routed through the entity/payload/knowledge-visibility system, since `Tenant` has no `entity_id` at all and a profile picture shouldn't be gated by machinery built for GM secrets. A user with no upload falls back to a computed Gravatar redirect when they have a verified email; tenants/campaigns have no such fallback. Picture-serving (`GET .../picture`) is the first unauthenticated resource route in this API - a plain `<img src>` can't send a Bearer token - while upload/delete stay fully authenticated and authorized as normal ([ADR 0056](../adr/0056-profile-pictures.md)).

A new `platform-operator` Authgear role (same mechanism as `tenant-creator`, ADR 0033) gates a new `/admin/*` surface, orthogonal to tenant membership entirely: `GET /admin/tenants` (platform-wide, unlike `GET /tenants`'s own caller-scoped list), `GET /admin/users` (a real `?q=` browse/search, unlike ADR 0055's deliberately exact-match public lookup), and `PUT`/`DELETE /admin/users/{id}/suspend` - a suspended account is rejected on its very next request, anywhere in the API, enforced centrally in `dependencies.get_current_user` rather than scattered per router ([ADR 0057](../adr/0057-platform-operations.md)).

Notifications now exist as an in-app inbox spanning four scopes - platform, tenant, campaign, and character - fanned out to one row per recipient at creation (`GET /me/notifications`, `POST /me/notifications/{id}/read`, plus one `POST .../notifications` route per scope, each reusing that scope's own existing management authorization). `create_membership` also fires a `tenant_invite` notification automatically, proving the system-triggered path end to end. No real delivery channel (email/push/webhooks) yet - deliberately out of scope, this codebase has none of that infrastructure at all today. The `notification` table reuses and extends the cross-tenant self-access RLS shape `player`/`campaign_gm` already established (`migrations/versions/a22dc991a926_*.py`), plus a third clause (`created_by = app.user_id`) needed because `INSERT ... RETURNING` re-checks a new row against the table's own `SELECT` policy - found the hard way when every platform-scope notification failed outright despite its own `INSERT` policy being permissive ([ADR 0058](../adr/0058-notifications.md)).

A fifth scope, `group` (`POST /tenants/{id}/groups/{group_entity_id}/notifications`), broadcasts to every player controlling any member of an existing `group` (ADR 0028/0045 - a bare entity named by `GroupMember` rows, always characters). Authorization is per-member and fail-closed: the caller must be able to manage *every* character in the group, not just some of them, reusing the exact "any one campaign is enough" rule `PATCH /characters/{id}`'s rename path already established - promoted out of that router into `campaign_access.can_manage_character` so it has one home, not two copies ([ADR 0059](../adr/0059-group-scoped-notifications.md)).

Four small, independent additions rounded out the user/tenant-admin surface. `MeOut` gained a fuller profile - `display_name` (non-unique, alongside the existing unique `nickname`), `pronouns`, `bio`, `locales` (this codebase's first native Postgres array column), `user_color` (a `#RRGGBB` hex string for shared UI to key off), and an always-present `picture_url` - with `PATCH /me` broadened from the single-field `NicknameUpdate` to a proper `exclude_unset`-based `ProfileUpdate`, matching `update_tenant`/`update_campaign`'s own PATCH convention; `display_name`/`user_color` also join `nickname` on the tenant roster, since "UI highlights" only make sense if other members can see them ([ADR 0060](../adr/0060-user-profile-expansion.md)). Every notification a single call fans out now shares one `batch_id`, letting `GET /me/notifications/sent` answer "did anyone read what I sent" from the sender's own side - no new RLS policy needed, since ADR 0058's `created_by = app.user_id` clause already permits exactly this read ([ADR 0061](../adr/0061-notification-sender-read-receipts.md)). `POST /tenants/{id}/memberships/bulk` invites several people in one call, gated by a single up-front `_require_owner` check (unlike `bulk_assign_item_instances`'s per-item re-check - tenant-OWNER-ness doesn't vary per item) and never all-or-nothing, the same `begin_nested()`-per-item pattern ADR 0044 established; `ProblemOut` moved from `schemas/items.py` to `schemas/common.py` as its second consumer ([ADR 0062](../adr/0062-bulk-invite-to-tenant.md)). Finally, a new `audit_log` table and `GET /tenants/{id}/activity-log` give tenant admins a first, deliberately narrow activity log - only seven named mutation points (membership create/bulk-create/update/delete, campaign create/delete, GM grant/revoke) call the shared `record_activity` helper, not an exhaustive record of every mutation in the API; platform-scope events like suspension are explicitly out of scope for this slice ([ADR 0063](../adr/0063-tenant-activity-log.md)).

`GroupMember` (ADR 0028/0045) finally gets a write surface: `POST`/`PATCH`/`DELETE /tenants/{id}/groups[/{id}]` create, rename, and retire a group (a fresh bare `Entity`, plus one `GroupMember` row per initial member - retiring one ungroups everyone but deliberately leaves the underlying `Entity` alone, since RFC 0001 never guarantees it wasn't also something else); `PUT`/`DELETE .../groups/{id}/members/{id}` add/remove one member idempotently; `POST .../groups/{id}/members/bulk` adds several in one call with a per-member "ok"/"error" outcome, the same never-all-or-nothing `begin_nested()`-per-item pattern ADR 0044/0062 already established; `POST .../groups/{id}/duplicate` clones an existing group's entire roster onto a fresh one. Authorization reuses `_require_can_manage_group` (ADR 0059) as-is for "does the caller have standing over this group at all," plus a new per-new-member `can_manage_character` check for anything being added ([ADR 0064](../adr/0064-group-write-api.md)). Item instances gain a bulk container move, `POST .../item-instances/bulk-move` - either every direct child of a given container, or an explicit id list, each relocated into a new container in one call, sharing `_perform_set_container` with the pre-existing single-item `PUT .../container` so the two can't drift, and the same per-item outcome/never-all-or-nothing shape `bulk-assign` already established ([ADR 0065](../adr/0065-bulk-item-instance-container-move.md)). Separately, container-capability - [ADR 0047](../adr/0047-item-catalog-search-and-container-convention.md)'s documented `is_container` boolean-`stat_definition`-in-`tags` convention - gains a first-class, computed `is_container` field on `ItemOut`/`ItemInstanceOut`: it mirrors whatever that tag already resolves to when one is set (authorial intent wins), and otherwise falls back to whether the item currently has anything directly `Containment`-ed inside it, `True` if so and still `None` if not (a merely-empty container stays indistinguishable from "unknown," not inferred `False`) - still no migration and no new hardcoded `v_item`/`v_item_instance` column the way `is_magical`/`is_cursed` have, just a read of the already-resolved `tags` list plus one already-established relationship (`Entity.contained_links`, ADR 0041) ([ADR 0066](../adr/0066-is-container-computed-field.md)). `title` gets the same "fall back to something always-present" treatment: empty (no description authored at all, the common case) now falls back to the item's own `name` rather than `null`, narrowing `ItemOut.title` from `str | None` to an always-populated `str` ([ADR 0067](../adr/0067-item-title-falls-back-to-name.md)).

The first client app on top of all this, [`apps/loot-bot`](../../apps/loot-bot) ([ADR 0050](../adr/0050-loot-bot-stack-linking-and-isolation.md)/[0051](../adr/0051-loot-bot-give-command.md)/[0052](../adr/0052-loot-bot-loot-drop-and-claims.md)/[0053](../adr/0053-loot-bot-http-interactions-and-cloud-run-deploy.md) — renumbered past 0042-0045 a second time on merge into `main`, which had independently claimed those numbers for the API additions in the paragraph above), is built against this now-real write API — the small `apps/api` addition it originally depended on (resolving "which characters does this user control," and letting a player read their own inventory without a tenant-wide `Membership` row) landed as part of the CRUD work above (`GET /me`'s `players[].characters[]`, ADR 0031; item-instance read-visibility narrowing, ADR 0040), so that dependency is closed. Its own deployment gap is closed too, on top of the same Cloud Run pipeline, once its Gateway-to-HTTP-Interactions rewrite (ADR 0053) is live. The concurrency-token, item-instance-slug, and read-only-groups additions above (ADR 0042/0043/0045) were themselves prompted by gaps this bot's own build surfaced - see each ADR's own Context section.
